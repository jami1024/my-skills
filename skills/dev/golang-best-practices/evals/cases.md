# Golang Best Practices 回归用例

## G1：新增服务端能力

**输入**

> 在现有 Go 服务中增加订单查询接口。项目已有 `cmd/`、`internal/handler`、`service` 和 `store`，请遵循现有结构。

**必须满足**

- 先读取 `go.mod`、入口、错误类型、配置和测试约定；
- 保持 handler、service、store 的依赖方向；
- 正确传递 context、处理错误、超时和资源生命周期；
- 运行 `gofmt`、测试、lint 或项目已有验证命令。

**失败信号**

- 创建巨大的 `utils` 包或全局数据库连接；
- 在 store 层返回 HTTP 状态码；
- 忽略 response body、超时或取消信号。

## G2：并发问题

**输入**

> 多个 goroutine 同时更新内存缓存，偶尔出现数据竞争。请修复并说明如何验证。

**必须满足**

- 这是单主题任务，不自动加载本地项目蓝图；已手动加载时转交 `golang-concurrency`；
- 先构造稳定复现或最小失败测试；
- 明确共享状态、生命周期和同步边界；
- 选择简单可解释的 mutex、channel 或其他方案；
- 运行 `go test -race ./...` 或项目等价命令。

**失败信号**

- 只增加 sleep 或重试；
- 用 `context.Background()` 隐藏调用方取消；
- 没有竞态验证就宣称修复。

## G3：非适用请求

**输入**

> 请优化一个 React 页面中的列表渲染性能。

**必须满足**

- 说明 Go skill 不适用于该请求；
- 不生成 Go handler、goroutine 或后端 API；
- 可以建议使用 React 专用 skill 或前端性能工具。

**失败信号**

- 把前端问题改写成 Go 服务优化；
- 建议无关的数据库或 HTTP 中间件改动。

## G4：Store 层事务与超时

**输入**

> 创建订单需要同时写 orders 和 order_items，任一失败整体回滚。项目用 GORM 和现有的 internal/store 包，请实现并说明超时怎么处理。

**必须满足**

- 事务放在 store 层，通过接口暴露给 biz 层；
- 由请求 context 派生带超时的 context，传给 GORM 的 `WithContext`；
- 沿用项目现有事务回调；回调返回错误时整体回滚，不为测试要求额外手写 `defer Rollback`；手动管理事务时检查开始、提交和必要的回滚错误；
- 说明如何验证：至少一个失败用例和一个超时用例；
- 复用项目现有 GORM 配置与 logger。

**失败信号**

- 在 biz 或 handler 里直接调用数据库事务；
- 用 `context.Background()` 创建事务；
- 只写成功路径，没有失败用例；
- 为本次改动引入新的 ORM 或迁移工具。

## G5：配置与密钥

**输入**

> 服务新增一个第三方 API 的接入配置：base URL、超时、API key。本地开发用环境变量，生产用密钥管理系统。

**必须满足**

- 区分缺失值与空值（`os.LookupEnv` 或项目已有配置库）；
- API key 只从环境或密钥管理系统读取，不进仓库、不进默认配置；
- 配置带默认值与校验，启动时失败要点名缺哪个变量；
- 日志与错误信息不回显 key。

**失败信号**

- 把 key 写进 `configs/` 或 `.env` 并提交；
- 用空字符串表示“未配置”；
- 启动后才在首次调用时发现配置缺失；
- 错误信息里带出完整 key。

## G6：可观测性与健康检查

**输入**

> 给现有 Go 服务补上 request ID、结构化日志、指标和健康检查，要求能区分进程存活与依赖可用。

**必须满足**

- request ID 在 middleware 生成并写入 context，日志与下游调用都用它；具体监控做法按需读取 `golang-observability`；
- `/livez` 与 `/readyz` 分开，readyz 检查数据库等依赖；
- 指标在边界处记录（请求量、延迟、错误）；
- 可观测代码不散落到 biz 层。

**失败信号**

- 把健康检查写成同一个端点且都查数据库；
- 在业务逻辑里直接上报指标；
- 日志里打印完整请求体或 Cookie；
- 每次请求新建日志器或指标对象。

## G7：迁移与容器交付

**输入**

> 本次改动新增一张表，需要在部署时应用；项目用 golang-migrate 和 Docker Compose。

**必须满足**

- 迁移文件成对出现（up/down），命名沿用项目现有规则；
- 在新库和已有库上分别验证 up 与 down；
- Compose 里服务等待数据库就绪；
- 交付说明写清迁移顺序与回滚方式。

**失败信号**

- 只写 up 不写 down；
- 手改数据库绕过迁移文件；
- 启动时自动执行迁移且不说明风险；
- 迁移版本号与项目现有文件重复或乱序。

## G8：已有项目重构

**输入**

> 现有 Go 仓库的 store 层直接返回 `gorm.ErrRecordNotFound`，biz 层把数据库细节透传给 API。请在不改对外 API 的前提下重整错误处理。

**必须满足**

- 先读现有错误类型、API 契约和测试，列出受影响的调用点；
- 在 store 层把数据库错误转换成领域错误，biz 层不再依赖 GORM 类型；
- 对外响应保持不变，有测试覆盖旧的响应格式；
- 遵循项目现有目录与命名，不顺手搬动包。

**失败信号**

- 改动对外响应结构或状态码；
- 顺手重命名包或调整目录；
- 没有覆盖旧行为的测试；
- 一次性改完所有层，无法分步验证。

## G9：授权与密码哈希

**输入**

> 新增“用户修改自己的资料”接口，需要确认操作者是资源所有者，且密码字段不出现在响应里。

**必须满足**

- 认证与授权分开，授权检查资源归属；
- 密码用成熟的密码哈希实现，字段与响应都不含明文；
- 敏感字段在序列化层显式排除，不依赖调用方自觉；
- 有越权访问的失败用例。

**失败信号**

- 只校验登录，不校验资源归属；
- 在 handler 里手写哈希或自造盐值方案；
- 用 `omitempty` 隐藏密码字段；
- 日志或错误信息里带出密码。

## G10：相邻领域转交

**输入**

> 线上 Go 服务最近偶发卡顿，帮我用 pprof 找到热点并给出优化方案。

**必须满足**

- 这是性能主题任务，直接读 `golang-benchmark`，需要根因分析时再补 `golang-troubleshooting`，不为任务自动加载本地项目蓝图；
- 取证发现项目结构、超时配置或资源生命周期确有问题时再扩大读取范围；
- 保留项目现有验证命令。

**失败信号**

- 在本 skill 内编造 pprof 命令与火焰图解读；
- 直接给出未经验证的优化改动；
- 忽略项目已有的指标与日志。

## G11：最小服务不预建分层

**输入**

> 新建一个标准库 Go HTTP 服务，只有健康检查和一个内存查询接口，手工组装依赖，本地运行。请给最小可运行实现，不需要数据库或容器。

**必须满足**

- 允许单包按职责分文件，不因参考资料提前创建 handler、biz、store、model 等层级；
- 只实现实际需要的行为、超时与退出处理；
- 使用标准库和手工构造，不引入 ORM、注入生成器或容器环境；
- 验证请求行为与正常关闭，运行适用的测试和构建。

**失败信号**

- 为目录模板创建空包或纯转发层；
- 自动安装 Wire 或增加 GORM、数据库、缓存服务；
- 要求 Docker Compose 才能运行测试。

## G12：沿用按业务能力组织的项目

**输入**

> 现有 Go 服务按 internal/orders、internal/inventory 组织，没有统一的 service/store/model 分层。请增加订单预留库存的用例，沿用现有目录、手工构造和错误契约，不改变 API。

**必须满足**

- 先读取两个业务包的实际入口、依赖接口、错误和测试；
- 保留按业务能力的组织方式，只为真实跨包调用定义最小契约；
- 明确预留失败、取消与重复请求行为，沿用已有事务或补偿方式；
- 用失败路径和兼容性测试验证范围，不额外创建统一聚合接口。

**失败信号**

- 搬到统一 handler/biz/store/model 目录；
- 为每个类型创建接口或为套分层新增纯转发代码；
- 参考资料中的工具组合覆盖了项目已有约定。
