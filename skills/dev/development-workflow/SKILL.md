# 软件开发工作流程

语言无关的通用开发流程和最佳实践。与具体技术栈的 skill（fastapi/golang/react-best-practices）协同使用。

内置模板（需求、设计、tasks、ADR、评审清单）和结构化文档编写流程。

---

## 核心开发流程

```
1. 需求引导      ──  理解目的、约束、成功标准
      ↓
2. 设计方案      ──  多方案对比、增量展示、用户审查
      ↓
3. 实施规划      ──  细粒度任务分解、生成 tasks 清单
      ↓
4. 代码实现      ──  按 tasks 执行、持续更新状态
      ↓
5. 代码审查      ──  功能/可读/安全/性能多维审查
      ↓
6. 测试验证      ──  测试金字塔、关键路径优先
```

---

### 复杂度评估

收到任务后，先评估复杂度再决定流程深度：

| 复杂度 | 特征 | 流程 |
|--------|------|------|
| **简单** | 单文件改动、明确的 bug 修复、配置调整、文案修改 | 直接执行，无需设计审批 |
| **中等** | 少量文件、逻辑清晰的小功能、已有模式的扩展 | 简要确认理解和方案，用户同意后执行 |
| **复杂** | 新功能、多模块影响、架构变更、技术选型 | 完整步骤 1-3：需求引导 → 设计方案 → 实施规划 |

<HARD-GATE>
**复杂任务**（新功能、多模块影响、架构变更）必须在用户批准设计方案后才能编写代码。
简单和中等任务不受此限制。
</HARD-GATE>

### 任务清单（Tasks）机制

`tasks` 是执行追踪机制，不是形式负担。需要跨多个文件、预计超过半小时、或存在明确依赖关系时，使用独立的 tasks 文件；短小且可一次完成的工作可用回复中的 checklist 追踪。

### 何时创建 Tasks

| 场景 | 要求 |
|------|------|
| **简单** | 单一动作或一次可完成的修改直接执行；如果出现跨文件依赖或明显范围扩展，再补建 tasks 文件 |
| **中等** | 通常在实施前创建独立 tasks 文件；若能在一次短迭代内完成，可使用回复 checklist，但必须记录验证结果 |
| **复杂** | 在实施规划阶段创建独立 tasks 文件；设计和任务计划获用户确认后再进入编码 |

### Tasks 清单格式

- 需要文件化追踪的中等和复杂任务创建独立 tasks 文件；命名应与需求/设计文档共用同一个主题前缀，采用 `<主题>_tasks.md`
- 如果同一任务已有需求/设计文档，直接复用相同主题前缀，例如：`用户导入_requirement.md`、`用户导入_design.md`、`用户导入_tasks.md`
- 如果项目已有文档目录规范，可使用等价独立路径，例如 `docs/tasks/<feature>.md`
- 宿主环境的原生任务/计划工具可以辅助同步状态，但不能替代这个 tasks 文件
- 回复中的 Markdown checklist 适用于简单任务，或适用于一次短迭代即可完成的中等任务；也可作为 tasks 文件的简短摘要
- 每个任务都要有稳定编号：`T1`、`T2`、`T3`
- 每个任务描述一个可验证的结果，不写模糊动作
- 一个任务应当对应一个可验证结果，通常可在 5-15 分钟内完成；跨多个职责或无法单独验证时继续拆分
- 一次只允许一个任务处于“进行中”
- 若被阻塞，保留未完成状态，并显式写出阻塞原因

```markdown
## Tasks
- [x] T1 明确需求边界和验收标准
- [x] T2 确认设计方案
- [ ] T3 编写失败测试：`tests/auth/test_login.py`
- [ ] T4 实现最小登录逻辑：`src/auth/login.py`
- [ ] T5 运行验证并整理结果
```

### Tasks 维护规则

1. 需要文件化追踪的中等和复杂任务在开始编码前先创建 tasks 文件
2. 每完成一个任务立即更新状态，不要等全部做完再回填
3. 范围变化时，先更新 tasks 文件，再继续执行
4. 完成任务时补充验证证据，例如测试命令、输出结论、相关文件
5. 结束时确保 tasks 文件与实际结果一致，未完成项必须说明原因

### Tasks 反模式

- 只写“继续开发”“完善功能”这类不可验证的任务
- 一边实现一边临时起意偏离计划，但不更新 tasks 文件
- 把多个文件、多类工作塞进一个大任务，导致无法判断进度
- 在任务完成后一次性批量勾选，丢失真实执行轨迹

## 1️⃣ 需求引导

### 探索项目上下文

在提问之前，先了解当前状态：

- 查看项目文件结构、文档、README
- 检查近期提交记录，了解项目动向
- 阅读相关代码，理解现有架构和模式
- 如果是现有代码库，**跟随已有模式**

### 评估范围

在问详细问题之前，先评估范围：

- 如果请求描述了**多个独立子系统**（例如"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记
- 帮用户拆解为独立子项目，每个子项目独立走完设计 → 规划 → 实施的完整周期

### 提问原则

| 原则 | 说明 |
|------|------|
| **每轮聚焦一个高价值问题** | 默认不要用多个问题压垮用户；若问题相互独立且用户希望一次收集，可合并 |
| **优先使用选择题** | 比开放式问题更容易回答，降低认知负担 |
| **逐步深入** | 先解决会阻塞实施的未知，再追问低风险细节 |
| **聚焦三个维度** | 目的（为什么做）、约束（不能做什么）、成功标准（怎么算做好了） |

### 提问聚焦方向

- **目的**：你想解决什么问题？谁来用？用在什么场景？
- **约束**：技术栈限制？性能要求？兼容性要求？时间限制？
- **成功标准**：怎么判断这个功能做好了？用户看到什么就算成功？
- **边界**：哪些是不需要的？明确"不做什么"和"做什么"同样重要

### 用户故事格式（可选）

对于需要文档化的需求，可使用用户故事格式：

```
作为 <角色>
我想要 <功能>
以便于 <价值>

验收标准：
- [ ] 具体标准 1
- [ ] 具体标准 2
```

## 2️⃣ 设计方案

### 多方案探索

对存在真实取舍的中等或复杂任务，不要直接给出未经比较的单一方案；简单任务或已有明确项目约定时可直接采用现有方案：

1. **提出 2-3 种不同方案**，每种附带：
   - 实现思路概述
   - 优点与缺点
   - 适用场景和复杂度评估

2. **给出推荐**，说明为什么推荐这个而非其他；如果没有有意义的替代方案，明确写出原因

3. **请求确认**后再深入细化；低风险方案无需人为制造选择题

### 增量展示设计

设计展示控制在用户可审阅的范围内，不要把无关细节一次性倾倒：

- **根据复杂度调整篇幅**：简单的几句话，复杂的 200-300 字
- **默认一次展示一份完整但简洁的设计，并在结尾请求确认**；只有存在高风险分歧或关键未知信息时，才分段确认
- 覆盖以下主题（按需）：架构概览、核心组件及职责、数据流向、错误处理策略、测试策略

如果用户不同意：回到对应环节澄清分歧，用户的判断优先。

### 架构决策记录（ADR）

对重要的技术决策（技术栈选择、架构模式、影响长期维护的决策），使用 ADR 记录：

```markdown
# ADR-001: 选择 PostgreSQL 作为主数据库

## 状态：已接受

## 背景
需要为新项目选择数据库，要求支持复杂查询、事务和高并发。

## 决策
选择 PostgreSQL。

## 原因
1. 强大的 ACID 事务支持
2. 丰富的数据类型（JSON、数组等）
3. 优秀的性能和可扩展性

## 后果
- 正面：稳定可靠，功能丰富
- 负面：相比 NoSQL 在某些场景下性能稍差
```

### 规格自审

设计展示完毕后，以全新视角审视：

| 检查项 | 具体做什么 |
|-------|-----------|
| **占位符扫描** | 搜索 "TBD"、"TODO"、"待定"。找到就修复。 |
| **内部一致性** | 各部分是否矛盾？架构和功能描述是否匹配？ |
| **范围检查** | 是否聚焦到可以写出一个实施计划的程度？ |
| **歧义检查** | 是否有需求可以被两种方式解读？选定一种并明确。 |
| **YAGNI 检查** | 是否包含了用户未要求的特性？砍掉。 |

发现问题就**直接修复**。

### 用户审查

自审通过后，请用户确认设计方案。简单任务不需要人为制造设计审批；中等任务至少确认范围和方案，复杂任务必须在实施前获得明确批准：

> "设计方案已整理完毕。请确认是否有需要调整的地方，确认无误后我会开始制定实施计划。"

**只标记会导致实施问题的内容**（缺失关键信息、内部矛盾、严重歧义）。不纠结措辞风格和格式偏好。

等待用户回复。用户批准后进入步骤 3。

## 📄 正式文档编写（可选）

当步骤 1-2 的产出需要形成**独立的正式文档**（需求文档、设计文档、ADR、技术规范）时，使用此流程。简单的设计确认不需要走此流程。

### 文档模板

| 模板 | 用途 | 路径 |
|------|------|------|
| 需求文档 | 用户故事、功能需求、验收标准 | `templates/requirement-template.md` |
| 设计文档 | 架构方案、API 设计、数据模型 | `templates/design-template.md` |
| ADR | 架构决策记录（选型理由、权衡分析） | `templates/adr-template.md` |
| 评审清单 | 架构系统化评审（11 维度 100+ 检查点） | `templates/architecture-review-checklist.md` |

使用方式：读取对应模板，按模板结构填充内容。

### 文档写作规则

- 先让读者在开头 30 秒看懂 4 件事：为什么要做、这次做什么、不做什么、怎么验证
- 优先用日常表达，不堆术语；必须使用术语、缩写或英文词时，第一次出现要用一句话解释
- 先写结论，再写背景和细节；段落尽量短，一段只讲一件事
- 标题尽量直接回答读者问题，例如“为什么现在做”“这次怎么做”“怎么验证”，少用空泛标题
- 只有对比、追踪或清单确实更清楚时才使用表格；普通说明优先短段落或短列表
- 模板是起点，不是所有章节都必须保留；对当前文档没有帮助的章节可以删除，或明确标注“不适用”
- 默认面向不了解上下文的读者，不假设对方已经知道内部缩写、历史背景或项目惯例

### 模板使用原则

- 需求文档和设计文档先填写核心部分：目标、范围、方案/需求、风险、验证
- 编号、追踪矩阵、关联文档等字段在需要追踪时再保留；如果项目不要求，可删掉或留空
- 面向非技术读者的文档，优先使用“需求、范围、影响、验证”这类词，少用“契约、可观测性、幂等性”这类术语
- 如果某一节只能靠堆术语才能写清，先改写节标题和摘要，再决定是否保留该节

### 读者测试

文档完成后，做一次读者测试；有可用的子 agent 时可委托给它：

1. **预测读者问题**：列出 5-10 个读者可能会问的问题
2. **独立阅读测试**：只给测试者文档内容和问题，检查能否正确回答
3. **补充检查**：指出文档中模糊、矛盾、术语过多或假设读者已有前置知识的地方
4. **修复**：针对答错或标记的问题，回到对应章节修改

当读者测试能回答关键问题且不再发现阻塞性歧义时，文档就绪；若当前环境没有可用的子 agent，使用同一组问题自行复核，并记录未验证的假设。

## 3️⃣ 实施规划

### Tasks 文件模板

需要文件化追踪的中等和复杂任务先创建独立 tasks 文件，再开始实施。默认命名规则为 `<主题>_tasks.md`；如果同一任务已有需求/设计文档，直接复用同一个主题前缀；如果项目已有规划目录规范，可使用等价独立路径。一次短迭代即可完成的中等任务可以用回复 checklist 替代，但仍要记录验证结果。

| 模板 | 用途 | 路径 |
|------|------|------|
| Tasks 清单 | 中等/复杂任务的文件化执行追踪、状态更新、验证记录 | `templates/tasks-template.md` |

创建 tasks 文件时，优先复制 `templates/tasks-template.md`。原生任务工具可以辅助同步状态，但不能替代这个文件。

### 基本原则

- **零上下文假设**：假设执行者对代码库不熟悉，写清一切
- **DRY**：不要重复自己
- **YAGNI**：不要实现不需要的东西
- **Tasks 文件先行**：需要文件化追踪的中等和复杂任务先创建 tasks 文件，再开始执行
- **状态可见**：每推进一步都更新 tasks 状态，让用户知道当前进度
- **测试优先但不机械套用 TDD**：对可测试的业务行为优先先写测试；文档、配置、样式或探索性改动按风险选择验证方式
- **提交边界**：只有用户明确授权后，才执行 `git add`、`git commit` 或 `git push`；未授权时只提供建议命令

### 文件结构规划

在定义任务之前，先列出将要创建或修改的文件及其职责：

- 每个文件应有一个清晰的职责
- 优先使用小而聚焦的文件
- 一起变化的文件应放在一起，按职责而非技术层级拆分

### 细粒度任务分解

每一步对应一个动作和一个可验证结果，通常控制在 5-15 分钟；不要为了凑步骤把一次性操作拆成无意义的碎片：

| 步骤类型 | 示例 |
|---------|------|
| 准备验证 | "为 `user_login` 补充边界测试，或为文档变更列出检查项" |
| 实现变更 | "实现 `user_login` 函数的最小代码" |
| 运行验证 | "运行项目已有测试、lint 或文档检查并记录结果" |
| 更新文档 | "同步受影响的 API、配置或使用说明" |
| 提交 | "用户授权后提交当前修改" |

### 先给 Tasks 总览

在展开详细计划之前，先创建或更新 tasks 文件中的顶部任务清单，用于追踪整体进度。详细步骤服务于执行，`Tasks` 服务于追踪，两者都要有。

需要文件化追踪的中等和复杂任务开始前，先复制 `templates/tasks-template.md` 生成 tasks 文件；简单任务或短小的中等任务可直接使用回复 checklist，范围扩展后再补建文件。

### 任务结构模板

````markdown
## Tasks
- [ ] T1：[组件名称] 明确验收标准和受影响文件
- [ ] T2：[组件名称] 补充测试或其他适合的验证方式
- [ ] T3：[组件名称] 实现最小变更
- [ ] T4：[组件名称] 运行验证并更新文档

### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1：准备适合本任务的验证**

业务逻辑优先写测试；文档、配置或样式改动可改用 lint、快照、构建或人工检查。

- [ ] **步骤 2：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 3：运行验证并记录结果**

运行项目已有的测试、lint、构建或文档检查命令。

- [ ] **步骤 4：同步文档和交付说明**

- [ ] **步骤 5：提交（需用户授权）**

只有用户明确授权 Git 操作后，才运行：

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 添加具体功能"
```
````

### 禁止占位符

以下是**计划失败**的标志——绝不允许出现：

| 禁止内容 | 说明 |
|---------|------|
| "TBD"、"TODO"、"后续实现"、"待补充" | 必须现在就写清楚 |
| "添加适当的错误处理" | 必须写出具体的错误处理代码 |
| "添加验证" / "处理边界情况" | 必须写出具体的验证逻辑 |
| "为上述代码编写测试"（不含测试代码） | 对业务逻辑必须给出具体测试；其他改动要写明适用的验证方式 |
| "类似任务 N"（不重复代码） | 必须重复写出完整代码 |
| 描述做什么但不展示怎么做 | 关键实现步骤必须给出代码、命令或可执行检查 |

### 计划自审

| 检查项 | 具体做什么 |
|-------|-----------|
| **规格覆盖度** | 逐条检查设计中的每个需求，是否都有对应任务？ |
| **Tasks 覆盖度** | tasks 文件中的 `## Tasks` 顶部清单是否覆盖了所有详细任务？是否能反映真实执行顺序？ |
| **占位符扫描** | 搜索"禁止占位符"列表中的所有模式。 |
| **类型一致性** | 后面任务中的类型、方法签名是否与前面定义的一致？ |

发现问题就**直接修复**。缺少对应任务就**补充**。

### 执行交接
