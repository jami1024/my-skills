# Learning Docs

生成一套能跟着做、能验证结果、能继续练习的技术学习文档。默认输出 Markdown；只有用户明确要求网页时才输出 HTML。

## 与 `explain` 的边界

| 用户需要 | 使用 |
|---|---|
| 解释一个概念、机制或一小段材料 | `explain` |
| 生成多步骤教程，带项目、命令、练习和排错 | `learning-docs` |
| 整理长期学习路径或一组循序渐进的文档 | `learning-docs` |
| 逐行讲解代码库或做代码审查 | 不使用本 Skill，改用代码分析或 review 流程 |

如果请求同时包含两者：先用 `explain` 解决当前概念，再用本 Skill 设计后续实践教程。

## 开始前确认

信息不足时，只询问会改变方案的问题：

- 读者已有基础和目标；
- 主题的版本、语言、框架和运行环境；
- 目标是入门、完成一个项目，还是建立长期学习路径；
- 是否需要可执行代码、练习、测试或发布结果。

如果用户没有指定，选择一个小而完整的项目作为主线，并明确假设。不要把多个框架或替代实现混在同一条教程路径里。

## 生成流程

### 1. 先给学习计划

复杂主题先生成 `{topic}-plan.md` 或先展示计划，包含：

- 学习目标和完成标准；
- 前置知识和环境；
- 按顺序排列的阶段与知识点；
- 主线项目及每阶段新增能力；
- 示例、练习和验证命令。

用户确认计划后再展开长教程；简单主题可以直接生成，但仍要先列出目标和步骤。

### 2. 设计一条主线

教程应围绕一个小项目推进。每一步回答：

1. 读者要完成什么动作；
2. 应该修改哪些文件或运行什么命令；
3. 应该看到什么结果；
4. 这一步引入了什么概念；
5. 失败时如何定位和恢复。

主体优先让读者动手，设计取舍、历史背景和替代方案放入“设计说明”或附录。

### 3. 编写并验证示例

- 代码必须与目标版本匹配；
- 新文件给出完整内容或明确的上下文；增量步骤说明修改位置；
- 运行命令、预期输出和实际行为一致；
- 能运行时实际执行 format、lint、test、build 或语言对应命令；
- 不能执行时明确标记“未运行”，不要声称已验证；
- 示例中的数据、版本和外部事实来自用户输入、官方文档或明确的假设。

## 推荐输出结构

```markdown
# {主题} 学习教程

> 完成后你能：{可验证目标}

## 你将构建什么
## 前置准备
## 学习路线
## 第一步：{动作}
### 修改或运行
### 你应该看到
### 这一步学到了什么
## 第二步：{动作}
...
## 综合项目与验证
## 常见问题与排错
## 练习
## 设计说明（可选）
## 下一步
```

不要为了“完整”强行添加四个附录。根据主题保留真正有用的排错、速查、FAQ 或练习。

## 写作规则

- 开头先给可验证的结果，不从术语百科开始；
- 一次只引入完成当前步骤所需的概念；
- 一条主路径优先，替代方案只在会影响决策时说明；
- 每一步都有可见结果或明确的验证方式；
- 术语首次出现时给出白话解释，必要时附术语表；
- 预判常见错误，但不要堆砌与当前环境无关的排错；
- 结尾给具体下一步，不写空泛的鼓励语；
- 中文简洁自然，中英文之间留空格，代码注释保持简短。

## 质量清单

### 目标与范围

- [ ] 读者、目标和前置条件明确；
- [ ] 主线项目足够小，能在合理时间完成；
- [ ] 版本、依赖和假设已标注；
- [ ] `explain` 与本 Skill 的职责没有混淆。

### 可执行性

- [ ] 每一步都有动作、文件或命令；
- [ ] 每一步都有结果检查；
- [ ] 最终项目有完整运行和验证路径；
- [ ] 预期输出与实际运行结果一致，未验证内容已标注；
- [ ] 练习有明确目标和检查方式。

### 内容质量

- [ ] 没有无依据的版本、数据或来源；
- [ ] 没有为了凑结构添加无关 FAQ、附录或替代方案；
- [ ] 排错建议能对应具体现象和原因；
- [ ] 代码遵循目标语言和框架的当前约定；
- [ ] 结尾给出可执行的下一步。
