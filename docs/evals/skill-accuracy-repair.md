# 准确性定向修复与复测

## 结论

保留精简结构，对归档事实边界、已有行为测试计划、SQLAlchemy 事务所有权做了窄范围修复。此前三个失败输入各回放两轮，**原先三类关键错误均未再现**；事务参考中的两个真实示例也通过了提交和回滚验证。

这不等于整体准确性无损。新场景中仍出现附加技术措辞错误和测试范围扩张；修复前在不少新场景本来就能答对。当前结论是已补上关键约束、已知错误有改善证据，仍需更多模型与独立场景验证。

## 改动

- `project-archive`：写入保证按失败阶段限定；diff 未覆盖的文件不因当前存在就标为新增/修改。两个归档模板同步增加“历史未知”和副作用边界。
- `development-workflow`：逐条对照当前实现/覆盖，再确定真实缺口。已满足行为允许直接验收，不为红绿流程制造失败；真正缺陷仍可先增加失败回归。任务模板沿用相同规则。
- `fastapi-best-practices`：主文要求核实事务所有者，并按需读取新增 `references/transactions.md`；结构参考中的服务示例明确新 session 入口，查询置于 begin 内。新增参考区分用例拥有事务、参与外层事务以及 autobegin。

修复后主文分别只比修复前增加约 273、130、274 字符，未恢复长篇通用教程。事务细节放在独立参考中，按任务读取。

## 运行设计

第一阶段：6 个新定向场景 × 修复前后 2 个版本 × 2 轮，共 **24 次真实模型运行**。输入与断言在修改完成和调用模型之前冻结，见 [场景与断言](skill-accuracy-repair-cases.json)。

修复前为上轮评估使用的精简版，不是最初的长文版。已有的少量归档编辑在隔离快照中反向恢复后，与上轮 `manifest.json` 的 SHA-256 逐文件核对一致；没有改回工作区文件，也没有 Git 写操作。修复后另建快照，运行期间不改快照。

模型为 `deepseek/deepseek-v4-flash-vision-exp`，thinking=`low`；工具只有 `read`，每次独立会话，关闭其他 skill、上下文文件、扩展及 MCP；显式注册并调用目标正文。两个进程并发，按轮次和场景交替提交版本顺序。模型只收到请求和项目夹具，不收到评分断言。

24 次均正常结束，实际读取路径未发现跨版本混用。修复后的四次 FastAPI 场景都自行读取了新的事务参考，输入没有指定参考文件名。

第二阶段：首轮修复后有一份回答仍把外层显式 begin 内的查询误称为触发 autobegin。只补充“内部查询参与显式事务，不会再次 autobegin”这一句后，冻结 `after-v2`，单独回放此前三个失败输入与该新场景，各两轮，共 **8 次**。没有把这批结果替换第一阶段样本，也不合并计算通过率。当前工作区哈希与 `after-v2` 一致。

总计本轮新增 32 次运行：24 次新场景对照 + 8 次单独回放。

## 新场景逐项判定

每个场景有 4 条预先冻结的核心断言；表中数字表示“当轮四条均满足”的轮次数，**不表示整篇回答完全准确**。附加错误另外保留，不被核心断言通过抵消。

| 场景 | 修复前 | 首轮修复后 | 主要发现 |
| --- | --- | --- | --- |
| 库存导入阶段与部分写入 | 2/2 | 2/2 | 两版均识别 quantity 在 extend 生成期间转换，失败可能保留前项；测试历史未知，没有测出增益 |
| 标签编码失败与无历史快照 | 2/2 | 2/2 | 两版均识别 ASCII 编码中途失败可保留已追加数据；不虚构旧实现/本次新增 |
| 已实现的零数量拒绝 | 2/2 | 2/2 | 均不改正确生产代码、不强造红灯；但多份回答仍把负数/边界测试当成本次必须补齐的缺口 |
| None 处理的真实实现缺口 | 2/2 | 2/2 | 均识别 AttributeError、需要新的失败回归，并保留 trims 成功；没有因避免机械 TDD 而放过真缺陷 |
| 外层已拥有请求事务 | 1/2 | 2/2 | 修复前 R1 错把再次 begin 说成形成嵌套事务/SAVEPOINT；修复后职责正确，但 R2 误称内部查询再次 autobegin，触发后续单独修正 |
| 新 session 用例拥有事务 | 1/2 | 2/2 | 修复前 R1 部分所有权调整建议混淆 SAVEPOINT 与最终提交；修复后两轮均明确 begin 入口、活动事务会报错及上移边界方式 |

24 份回答的 96 条人工断言判定、行号证据、附加问题，以及单独回放判定见 [逐项记录](skill-accuracy-repair-verdicts.json)。证据摘录是定位辅助，语义判定为人工审阅，不是关键词自动打分。

## 已知失败输入回放

对最终 `after-v2` 使用旧输入、旧只读夹具，各两轮；不是新场景泛化证据：

| 原失败点 | 本轮 2 次输出 |
| --- | --- |
| 归档把查重前零写入扩大为任何异常都零写入 | 均区分前置校验与 extend 中途异常，指出部分写入可能；测试未在 diff 中时均写历史未知 |
| 已有去重却要求先红灯再实现 | 均发现既有实现及根目录测试，已满足时不改动，不要求人为失败，不换 pytest |
| SQLAlchemy begin 被写成自动复用活动事务 | 均明确新 session 与外层事务所有权，活动事务上重复 begin 抛 InvalidRequestError，不宣称自动复用 |
| 首轮新增的显式事务内查询误称 autobegin | 两轮均未再出现这一表述；正确说明已在外层显式事务中 |

仍需保留的附加问题：外层事务复查 R2 写了“进入 begin 前没有已提交事务”，应为“没有活动事务”；同段下一句说明已有查询会导致重复 begin 报错，核心建议仍成立。开发计划复查 R2 还出现“无未覆盖分支”的绝对化验收，现有两个测试不能证明这一点，且“异常时 store 不变”应明确限定重复校验失败。它们不作为旧关键错误消失的抵消项，也不据此称全文通过。

## 实际代码与夹具验证

从当前 `transactions.md` 提取两个原始函数示例，在 SQLAlchemy 2.0.46、aiosqlite 内存 SQLite、真实 AsyncSession 中执行，没有用改写函数替代原文：

| 验证 | 结果 |
| --- | --- |
| 新 session、用例拥有事务，两次写入成功 | 用户/审计各新增 1 条 |
| 新 session、审计写入后注入失败 | 两者均无新增 |
| 外层 begin + 身份查询，内部用例参与，成功 | 两者均新增，内部未提前结束外层事务 |
| 外层 begin + 身份查询，审计失败传播 | 两者均无新增 |

夹具本身也已核验：库存、预订、格式化的现有 unittest 均通过；库存第二项 quantity 转换失败时保留第一项，标签第二项 ASCII 编码失败时保留第一项，format_label(None) 确实抛 AttributeError。它们分别确认两个阶段边界反例、已满足行为与真实缺口。
