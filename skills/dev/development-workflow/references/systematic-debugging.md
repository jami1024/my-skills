# 系统化调试

本参考只在出现 bug、失败测试、异常行为、偶发故障或性能回归时读取。正常的新功能实现不需要套用完整调试流程。

## 目标

先用证据定位根因，再修改根因所在边界。不要把“测试暂时通过”当成已经解释了问题。

## 流程

### 1. 固定症状

记录：

- 预期行为和实际行为；
- 最小复现步骤、输入、环境和时间范围；
- 完整错误信息、堆栈、日志和失败测试；
- 是否稳定复现，最近什么变更可能相关。

无法稳定复现时，先增加可观测性或收集更多样本，不要直接猜修复方案。

### 2. 缩小范围

沿数据流和调用链逐层检查边界：输入 → 转换 → 状态 → 外部依赖 → 输出。优先使用最小探针、日志、断言、二分或单个失败测试验证假设。

每次只验证一个主要假设，并记录：

```text
假设：
证据：
结果：支持 / 排除 / 不确定
下一步：
```

### 3. 确认根因

修改前应能回答：

- 哪个条件触发了问题？
- 哪个边界首次产生错误状态？
- 为什么现有测试或监控没有发现？

如果只能描述症状，继续调查，不要用大范围重构掩盖不确定性。

### 4. 修复并防回归

- 在根因所在层做最小修复；
- 为稳定复现的问题补充回归测试或等价自动检查；
- 只在证据表明需要时扩大修复范围；
- 运行针对性验证，再运行受影响的回归检查。

## 禁止模式

- 未复现就连续尝试多个猜测性补丁；
- 只增加重试、超时或忽略错误来隐藏症状；
- 把无关重构混入 bug 修复；
- 看到一次绿色测试就宣称问题已解决；
- 删除失败测试或放宽断言以消除红灯。

## 交付记录

结束时说明：症状、根因、修复文件、回归验证、仍未覆盖的风险。若根因或验证仍不确定，明确标记为未解决，不要使用“已修复”。
