# Go 工程改动工作流

在新增服务、跨模块改动或项目级工程审查时读取。核心约束见 [`../SKILL.md`](../SKILL.md)，包边界选择见 [`architecture-patterns.md`](./architecture-patterns.md)。通用需求与设计流程按需使用 `development-workflow` skill，本文只描述 Go 工程改动的实施和验证。

## 1. 锁定行为与现有约定

先找真实入口和一个相近实现，沿调用链确认受影响的包、接口、外部依赖与测试命令；不要求固定阅读几个例子，也不预设项目必须分成哪些层。

记录本次需要新增或保留的可观察行为：输入、输出、错误、权限、取消、事务与兼容性。修改范围不清楚时，先解决会影响实现的未知项。

已有功能改动只整理相关调用点。新服务先确认运行方式、协议、存储和关闭要求，再给出满足当前规模的最小组织方式；没有使用数据库、认证或容器的需求时，不提前加入这些模块。

## 2. 选择反馈最快的实现切片

| 任务 | 合适的起点 | 第一份有效证据 |
| --- | --- | --- |
| 修复错误或回归 | 最小复现、失败测试 | 修改前可复现，修改后不再失败 |
| 对外接口已确定 | 契约或请求级测试 | 输入、状态与响应格式被约束 |
| 核心计算或业务规则变化 | 规则函数与行为测试 | 成功、失败和边界行为明确 |
| 数据访问或事务变化 | 项目现有数据库夹具 | 提交、回滚、取消与隔离行为 |
| 现有结构重整 | 调用点与兼容性测试 | 对外 API 和已有行为保持 |
| 新建小型服务 | 最小可运行入口与一条用例 | 能启动、响应并正常退出 |

可以纵向完成一条用例，也可以先实现依赖；顺序服务于反馈速度。不要为了自底向上的流程先建数据模型、空接口和纯转发包。

## 3. 修改真实边界

对每个受影响的操作检查适用项：

- **协议与调用方**：复用现有参数校验、认证授权和响应约定，不额外创建统一响应框架。
- **业务规则**：规则和资源授权放在稳定归属处，跨入口复用时不依赖某个传输框架。
- **外部调用**：沿用现有驱动或客户端，传递请求 context，处理超时、错误和资源关闭。
- **错误转换**：特定驱动错误在适当边界映射为项目领域错误；其他错误添加操作上下文并保留原因，不向响应泄漏内部信息。
- **原子性**：复用已有事务机制，验证部分失败不会留下不完整状态；外部副作用另行说明幂等与重试。
- **应用组装**：新增依赖接入原有构造与生命周期，不默认引入注入生成器、全局连接或容器环境。

只修改任务需要的边界。项目没有独立 service、store 或 model 包时，不为符合这些检查项而搬包。

## 4. 选择与风险匹配的验证

测试断言真实行为；命名、目录、build tags、断言库与 mock 方式沿用项目约定。没有相应外部依赖的改动，不补无关的数据库或容器测试。

| 风险 | 优先验证 |
| --- | --- |
| 规则或边界输入 | 成功、错误、空值和边界值 |
| API 兼容性 | 现有状态、响应字段和错误结构 |
| 数据变更 | 提交、失败回滚、取消与迁移兼容性 |
| 并发或生命周期 | 竞态、退出、取消、清理与重复关闭 |
| 认证和敏感信息 | 未登录、越权、日志和响应脱敏 |
| 工具生成或依赖变更 | 锁定版本、生成结果、构建与 CI |

先运行受影响的测试和项目已有检查，再按影响扩大到完整测试、竞态与构建；命令阶梯见主 skill。长耗时集成检查按环境条件执行，无法运行时说明缺少的条件，不将其标记为通过。

覆盖率用来发现遗漏，重点审查业务分支和高风险行为；不为所有项目设固定覆盖率百分比，也不为了达标增加重复断言。

## 5. 审查改动范围并交付

提交结果前核对实际 diff：

1. 是否顺手移动目录、重命名公共类型或新增了不必要的抽象？
2. 是否保留原有 API、错误语义、context 传播与生命周期？
3. 是否因为示例引入了 ORM、注入工具、日志库或部署方式？
4. 测试是否覆盖此次变化，运行记录是否能支持完成声明？
5. 涉及配置、数据库或部署时，是否说明兼容性、执行顺序与恢复方式？

交付说明写清改动行为、已执行验证和未验证范围。需要用户决策的接口或存储变化应在实施前说明；Git 写操作仍遵循用户授权。
