# 项目技术归档

为接手开发者记录实际实现、接口、设计依据和风险。信息来自代码、配置、测试及可见对话；`handoff-summary` 负责会话决策和下一步，本 skill 负责项目与功能事实。

## 模式与读取范围

| 用户目标 | 模式 | 默认读取与产物 |
| --- | --- | --- |
| 项目、阶段或版本归档 | 项目归档 | 核心模块、运行与部署约定；新建项目文档 |
| 归档某个功能、补功能文档 | 功能归档 | 目标入口、状态流转、数据与测试；新建功能文档 |
| 代码变更后同步已有文档 | 文档更新 | 目标文档、相关 diff 与实现；增量更新 |

先复用用户明确的范围、路径和已有上下文；只有未决问题会改变扫描或写入范围时才询问。已要求更新指定文档时，读取并修改该文件，不重复请求同一授权。

## 开始前

1. 从请求和可见会话确定模式、范围及目标读者。
2. 查看相关目录、依赖配置和 Git 状态；功能归档或局部文档更新只扫描强相关模块，不默认遍历整个项目。
3. 读取实际入口、调用链、数据结构、配置、测试和已有文档，建立结论对应的文件与行号。
4. 新建文档优先使用用户路径或项目已有文档目录；没有约定时使用 `agent-doc/reference/`。版本未知时使用 `<功能模块>_context.md`，不编造版本号。
5. 仅对当前模式读取一个模板。模板中的例图、字段和章节都是起点，交付时替换或省略。

## 项目归档

按需读取 [`templates/project-context.md`](templates/project-context.md)，重点覆盖：

- 业务目标、完成状态和归档范围；
- 实际组件、入口、核心数据与交互流程；
- 重要接口、配置、迁移、依赖和构建运行命令；
- 已运行的验证、已知风险和后续工作。

文件名可使用 `v<版本>_<功能模块>_context.md`。仅记录实际存在的架构，不为了模板补造数据库、服务层或设计模式。

## 功能归档

按需读取 [`templates/feature-context.md`](templates/feature-context.md)：

1. 锁定入口、关键状态、数据访问、外部依赖及测试。
2. 通过实际代码解释调用链和边界，包含必要的路径与行号。
3. 只有存在可核验的 diff、历史版本或会话记录时，才区分“原有实现”与“本次变更”；无法核实历史时明确说明，只描述当前状态。仅看到文件当前存在，不足以断定它是新增或修改。
4. 聚焦功能相关风险与接手建议；数据保证按下方“证据与事实边界”限定阶段，不扩写无关模块。

命名规则与项目归档相同。不适用的 API、数据库和本次迭代章节可省略。

## 文档更新

1. **确定目标**：采用用户指定路径；未指定时根据变更和现有文档定位。多个候选且无法判断时再提问。
2. **读取原文**：读完目标文档，理解结构与上下文。
3. **核对实现**：检查相关 diff 和当前代码，区分代码事实、历史说明及待确认信息。
4. **局部修改**：在原有结构中新增、纠错或移除过期说明；涉及流程变化时更新对应图示，不默认重写全文。
5. **复核交付**：检查引用、链接和变更范围，遵循项目已有更新记录格式；没有约定时可追加 `Updated on <日期> for <原因>`。

重要变更可用简短说明突出；不强制使用特定 callout 或增加无关栏目。

## 证据与事实边界

- 代码事实优先于对话记忆；关键行为引用实际存在的文件和行号。
- 设计原因只有在注释、ADR、提交说明或对话中有依据时才确定陈述；其余标记为推断或待确认。
- 当前 Git diff 只能支持该 diff 覆盖范围内的变更判断；不能据此断言未显示文件“新增”或“修改”。无历史证据时标为“当前存在，历史状态未知”。
- 对数据写入、事务、原子性等保证，指出保证在哪个阶段开始和结束；写入前校验失败不等于写入中途失败也能回滚。检查实现的容器/数据库语义，不把单次 API 调用或语法结构直接视为事务。
- 配置记录名称、来源和非敏感默认值，不复制真实密钥、令牌或密码。
- 文档列出的命令不等于实际运行；明确区分已通过、失败、未运行和未覆盖。
- Git 状态和历史只用于取证，本 skill 不自动提交、推送或修改业务代码。

## 交付前检查

- 文档范围是否与请求一致，现有结构是否得到保留？
- 架构、接口、路径和图示是否与当前代码一致？
- 本次 diff 标记新增/修改的代码是否有直接证据？未纳入 diff 的文件是否被错误标记成新增或修改？
- 对异常和写入失败的保证是否限定在实际验证过的阶段？
- 是否删去了空模板、占位图和不适用章节？
- 是否保留已知风险，避免把“未发现”写成“没有风险”？
- 是否报告实际新增或修改的文件及验证限制？

没有写入时，明确交付的是建议或报告，不声称文档已同步。
