# 软件开发工作流程

负责需求、设计、计划、审查和验证的通用方法。具体实现遵循项目约定与对应技术栈 skill；不要为走流程加载无关指导或创建成套文档。

## 按任务选择深度

| 任务 | 默认做法 |
| --- | --- |
| 明确的单文件修复、配置或文案修改 | 定位、修改、运行相关检查，直接交付 |
| 少量文件、逻辑明确的小功能或既有模式扩展 | 简述范围和方案后执行，仅对影响结果的未决取舍提问 |
| 多模块新功能、架构调整或技术选型 | 先勘察需求和设计，再组织计划与实施；复用已有设计和授权 |
| 用户只要需求、设计、计划或审查 | 交付指定产物，不自动进入实现 |

复杂程度决定分析深度，不自动产生审批要求。用户明确的范围、已提供的设计和项目既有约定直接采用；只对无法自行核实且会改变范围、兼容性、成本或最终行为的关键未知请求决策。涉及持久化数据、兼容性或不可逆操作时遵循宿主与项目的授权规则。

## 1. 需求与范围

提问前先查看相关 README、配置、实现和测试；近期提交仅在需要理解演变或变更范围时读取。

确定四件事：

- **目的**：谁遇到什么问题，为什么要做；
- **范围**：本次行为与明确不做的内容；
- **约束**：现有技术栈、环境、兼容性、权限和资源；
- **验收**：用什么输入、可见结果或检查证明完成。

不重复询问已有答案。低风险缺失可以说明假设后继续；关键未知先勘察，再问聚焦的问题，优先提供易判断的选项。多个互不依赖的问题可合并，避免逐轮等待。包含多个独立子系统时，先分清边界与依赖，再按可验证的切片推进。

## 2. 设计与取舍

先采用项目现有模式。只有存在真实取舍时比较 2–3 个方案，说明收益、代价、适用条件并给出推荐；没有有意义的替代方案时，不为比较而制造选项。

设计按需覆盖职责、输入输出、数据流、错误处理、状态或资源生命周期、兼容性与验证方式。篇幅与风险匹配，默认一次给出完整且简明的方案。

自审后继续：

- 需求和接口是否一致，是否遗漏关键失败路径？
- 是否加入用户未要求的功能、依赖或抽象？
- 未知项能否通过项目资料或小型验证解决？
- 剩余歧义是否真的需要用户决策？

已获授权且设计足够时直接实施；只有阻塞性取舍才请求确认，并说明对后续的影响。重要且有长期维护价值的选择使用 ADR，记录背景、决策、理由、后果和替代方案。

## 3. 计划与 Tasks

### 何时文件化

存在跨文件依赖、预计超过半小时或需要跨轮追踪时，实施前创建独立 tasks 文件。简单任务及一次短迭代可完成的中等任务可用回复 checklist；范围扩展后再补建文件。

- 命名采用 `<主题>_tasks.md`，与已有需求、设计文档共用主题前缀；项目已有目录规范时优先采用。
- 需要文件化时，按需读取 [`templates/tasks-template.md`](templates/tasks-template.md)。宿主任务工具可辅助同步，但不替代该文件。
- 每项使用稳定编号 `T1`、`T2`，描述一个可验证结果；跨职责或无法独立验证时再拆分，不按固定时长制造碎片。
- 顶部 checklist 对应详细任务，一次一个任务标为进行中。

### 计划写什么

先将验收标准逐条对照当前实现、已有测试和实际命令，明确“已满足、缺测试、缺实现、尚未核实”，再列任务。文件与命令以实际项目为准，不因请求中的示例路径不存在就新建一套测试或换测试框架。

写清真实缺口对应的受影响文件、行为变化、依赖顺序、验证命令和完成标准。例如：

```markdown
## Tasks
- [ ] T1 对照 importer.py 与现有测试核实大小写规范化和写入边界
- [ ] T2 仅为尚未覆盖的验收行为补充回归，沿用实际测试路径
- [ ] T3 仅在确认行为缺口时修正导入逻辑，沿用现有错误格式
- [ ] T4 运行项目既有检查；若实现与覆盖已满足，记录无需改动
```

计划应消除实施歧义：错误路径写明触发条件、预期行为及验证方式；关键算法、接口或复杂边界必要时给出精确示例或伪代码。不要预写所有生产和测试代码；公共步骤和既有设计使用明确引用复用。

未知信息标为待确认并列出最小核实动作，不用猜测的类型、接口或实现填满模板。阻塞项写明原因，其余独立工作继续推进。

### 执行时维护

1. 开始前检查任务覆盖了本次范围和验收标准。
2. 范围变化先更新任务，再继续；每完成一项及时更新状态和验证证据。
3. 结束时核对 checklist 与实际结果，未完成项保留并说明原因。

用户只要计划时在交付后等待；用户已要求实施时按计划继续，不再要求选择“执行还是审阅”。

## 4. 实现、审查与验证

小步实现，每一步保持可检查。复用现有职责边界和依赖，不为形式重构无关代码。

- 业务规则和 bug 修复优先考虑可复现的行为测试；只有确认行为尚未实现或存在缺陷时，才预期新回归在修复前失败。已有行为和覆盖可直接通过，不为红绿流程破坏正确代码、重复实现或制造失败；文档、配置和样式按风险选择其他验证。
- 审查关注功能、可读性、安全、性能、错误诊断和测试，区分必须修复的问题与建议，给出文件位置和依据。
- 优先运行项目已有的相关检查；范围或风险需要时再扩大到集成、竞态、构建或端到端验证。
- 声称完成前核对命令退出码、关键结果和实际产物，区分通过、失败、未运行和未覆盖。
- 按变更同步相关 API、配置、文档和交付说明，不把建议命令当作执行结果。

Git 写操作仅在用户明确授权后执行，覆盖 `add`、`commit`、`push` 等；用户要求的实现和验证不自动包含 Git 提交。分支、提交格式和 CI/CD 遵循项目现状。

## 正式文档（按需）

只有用户要求或当前决策确实需要留存时才创建需求、设计或 ADR。先读 [`templates/README.md`](templates/README.md) 选择模板，再读取所需文件，不默认生成一整套。

| 当前需要解决的问题 | 模板 |
| --- | --- |
| 做什么、为什么做、如何验收 | [需求](templates/requirement-template.md) |
| 怎么实现、为什么这样选择 | [设计](templates/design-template.md) |
| 按什么顺序实施、如何证明完成 | [Tasks](templates/tasks-template.md) |
| 哪项长期决策需要记录 | [ADR](templates/adr-template.md) |
| 方案能否交付或上线 | [架构评审](templates/architecture-review-checklist.md) |

已有完整需求或设计时直接复用；只要计划时不重复生成同内容文档。开头简述选用模板的原因，删除不适用章节、占位内容和无关追踪字段。

写作先让读者理解目标、范围、影响和验证；先结论后细节，术语首次使用时解释。表格用于比较或追踪，不替代普通说明。

正式文档完成后，用读者可能提出的关键问题自检：能否仅凭文档找到正确答案、是否有模糊或矛盾、是否暗含未说明的前置知识。有可用的独立审阅者时可委托；没有时自行复核并记录限制，不假称独立测试已通过。
