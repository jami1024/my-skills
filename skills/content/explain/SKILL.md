# Explain Clearly

统一处理学习类请求。先区分概念解释、具体文章的解读、项目教程与陪练；不要让同一请求同时触发多个学习 Skill。用户要求存入 wiki 或写公众号成稿时，分别使用对应的 library 或 draft 流程。

## 模式选择

| 用户目标 | 模式 | 默认产物 |
|---|---|---|
| 理解一个概念、机制或产品 | 概念解释 | 直接讲解，按需补例子 |
| 总结或读懂一篇具体文章 | 文章解读 | 围绕来源主线的讲解，保留理由、例子与关键限定 |
| 学习一门语言、框架、工具或完整主题 | 项目教程 | 学习计划、主线项目、分步代码、验证和排错 |
| 学过之后要被提问考核、确认真的掌握 | 陪练 | 逐题提问、级别进度、间隔复习，不产出文档 |
| 只问一个具体问题 | 概念解释 | 直接回答，不强行生成完整教程 |
| 逐行理解代码库、查 bug 或做 review | 不使用本 Skill | 使用代码分析或审查流程 |

默认输出 Markdown；用户明确要求网页时才输出 HTML。

## 输出尺度

用户只问一个具体问题或要求一句话时，先直接回答，必要时只补一个例子。下文的类比、术语表、自测题和完整章节仅在帮助理解时使用，短答可全部省略；质量清单按所选尺度检查。

## 先确定教学任务

开始前明确：

- **目标**：读者学完能解释、判断或完成什么；
- **基础**：读者已经知道什么；
- **边界**：本次不覆盖哪些高级细节；
- **假设**：版本、运行环境、输入材料和未确认事实。

只询问会改变答案的问题。信息不足但风险低时，明确假设后继续。

## 概念解释模式

适合短回答、一页教学材料和“讲人话”。按主题取舍以下结构：

```markdown
# 主题
## 学习目标
## 先说结论
## 一个类比（说明类比的失真边界）
## 它实际怎么工作
## 最小例子
## 常见误解与边界
## 术语表
## 自测题或下一步
```

写作顺序：

1. 先给结论，不从术语定义开头；
2. 用一个熟悉的类比，再说明它哪里不准确；
3. 把机制拆成不超过 5 个连续步骤；
4. 关键术语首次出现时给白话解释；
5. 用最小例子验证机制；数字、人物和事实来自输入或明确标为假设；
6. 说明常见误解、适用边界和什么时候不该用；
7. 结尾给 2–3 个自测问题或具体练习。

不要为了“完整”堆砌历史、背景和无关术语。

## 文章解读模式

用于用户提供具体文章并要求总结、解读或“讲人话”。组织依据是来源的问题与论证，不套概念教程的章节。

1. 完整读取可用正文；搜索摘要或预览不能代替正文。材料不完整时说明覆盖范围，不补写未读部分。
2. 起草前在内部用一句话写出作者主要讨论什么、给出什么答案，再梳理论证如何支持答案。按材料实际的因果、问题与方案、对比或观点交锋组织；多主题来源保留各条主线，不强行拼成一个结论。用户未要求时不展示写前提纲。
3. 开头直接讲核心问题和答案，正文沿论证推进；标题和篇幅体现主次，不把支撑观点改成全文主题，也不把文章改写成通用行动清单。
4. 优先用来源中有解释力的场景、行为变化或例子讲清问题，再引入术语。首次出现的术语给白话解释；额外背景、类比、例子或建议须明确是解释者补充，且不能抢占来源主线。不得为增强感染力添加原文没有的焦虑、动机、评价或因果。
5. 保留影响结论的反例、适用条件、发言者归属和不确定性；引用就近给来源定位，同类获取与核实说明集中一次。术语表、自测题、练习和固定章节只在用户需要时添加。

写完后，分别用一句话概括来源与成稿的核心问题；若两者不同，先重排内容。表达更顺口不能以改变作者立场、结论强度或论证重点为代价。

## 项目教程模式

适合新语言、框架、工具或需要系统练习的完整主题。

### 1. 先给学习计划

复杂主题先给出简明学习计划；仅在用户只要求规划、或存在会改变学习路线的关键未知时等待确认。用户已提供目标与基础并要求完整教程时，说明计划后继续展开，不重复审批；小主题可直接生成目标、步骤和示例。只有用户要求文件或任务确需留存时才写入 `{topic}-plan.md`。

计划覆盖：

- 学习目标，以及可判定的完成标准（能预测、能解释、能独立完成什么，而不是勾掉章节）；
- 拆出的 4–10 个子技能，以及本次教程覆盖到哪几个；
- 前置知识、版本和环境；
- 按顺序排列的阶段与知识点；
- 主线项目及每阶段新增能力；
- 示例、练习和验证命令。

### 2. 设计一条主线

围绕一个小项目推进。每一步都说明：

1. 要完成的动作；
2. 要修改的文件或运行的命令；
3. 应该看到的结果；
4. 这一步引入的概念；
5. 失败时如何定位和恢复；
6. 一个要求读者先自己作答再继续的检查点问题（预测结果、解释原因或指出错误说法），以及答案在哪一步能验证。

主体让读者动手；设计取舍、历史背景和替代方案放到“设计说明”，不要混入每一步。

### 3. 编写与验证示例

- 代码与目标版本匹配；
- 新文件给出完整内容，增量步骤说明修改位置；
- 运行命令、预期输出和实际行为一致；
- 能运行时执行 format、lint、test、build 或语言对应命令；
- 不能运行时明确标记“未运行”，不声称已验证；
- 示例中的数据、版本和事实来自输入、官方资料或明确假设。

### 推荐教程结构

```markdown
# {主题} 学习教程
> 完成后你能：{可验证目标}

## 你将构建什么
## 前置准备
## 学习路线
## 第一步：{动作}
### 修改或运行
### 你应该看到
### 这一步学到了什么
### 检查点（先答再继续）
## 第二步：{动作}
## 综合项目与验证
## 常见问题与排错
## 练习
## 设计说明（可选）
## 下一步
```

不要强制添加固定数量的附录、FAQ 或替代方案。

“综合项目与验证”按混合测评组织：每个子技能至少一题，加一道串联多个子技能的整合题，并写明每题通过与否的判断方式。教程是静态产物，检查点让读者自问自答，不等待回答；需要持续提问考核时，交付后引导用户切换到陪练模式。

## 陪练模式

用于用户已经学过某主题、明确要求被提问考核而不是听讲。产物是会话过程而不是文档：不生成教程、不输出章节、不写文件。

用户意图不明确时先问一句（“要一份材料，还是我逐题带你练？”）；答要材料就回到上面三种模式。默认不进入本模式。

### 1. 建立技能地图

把主题拆成 4–10 个具体子技能，然后一次问一个，用 3–5 个由易到难的问题做诊断，定位各子技能起点。诊断完成前不讲解新内容。

按 0–5 级追踪每个子技能：

```text
0 没听说过 · 1 听过 · 2 能跟得上 · 3 能带着做
4 能独立做 · 5 能讲清并处理边界情况
```

每次级别变化后、以及用户要求看进度时渲染进度图：

```text
Topic: <主题>                          overall: ######.... 58%
-----------------------------------------------------------------
子技能 A              [########..]  4/5  * 独立完成
子技能 B              [######....]  3/5  <- 当前重点
子技能 C              [##........]  1/5
-----------------------------------------------------------------
```

进度图只出现在会话里，不写进任何教程或文件。

### 2. 提问循环

- 一次只问一个问题，问完立即停止，不加提示、示例答案或讲解；
- 优先要求用户预测结果、解释原因、找出看似合理但错误的说法中的漏洞、把概念用到新场景、连接两个概念；
- 答错时不直接给答案，换一个更窄的问题暴露矛盾；连续 2–3 次失败后才讲解，讲完立刻从另一个角度重测；
- 答对时偶尔追问（“确定吗？如果 X 成立会怎样？”），要求能在压力下守住正确答案；
- 只对用户无法自行推导的新材料做简短讲解，随后回到提问；
- 有执行环境时出可验证的题（写查询、预测代码输出、跑测试），看实际输出而不是用户对输出的描述。

### 3. 评级从严

- 级别靠表现挣得：升级需要 2 次以上独立检验，其中至少一次是无提示回忆，而不是刚被告知答案后立刻复述；
- 含糊或部分正确的回答不算正确，追问到能判断用户是否真的理解为止；不把用户没说过的洞察算成他懂；
- 定期无预告复测早前子技能，失败则降级并重讲；
- 5 级要求能处理边界或对抗性问题，并讲得清楚到可以把这件事交给用户去教别人；
- 不奉承。“不太对——如果 Y 成立，X 为什么还会发生？”优于“很好的尝试”。

### 4. 结束与状态

所有子技能达到目标级别（默认 4；用户要求完全掌握则 5）后做一次混合测评：每个子技能至少一题，加一道整合题。通过则给出最终进度图和薄弱点总结；未通过回到循环。

用户可随时使用：

- “看进度”——渲染进度图；
- “难一点” / “简单一点”——调整难度；
- “直接告诉我”——仅当前问题退出提问模式；
- “保存状态”——输出紧凑状态块（主题、各级别、误解笔记、已覆盖内容）供新会话续接，格式沿用 `handoff-summary`，不写进教程正文；
- “从状态继续：”——接一段保存的状态块并恢复。

## 通用写作规则

- 开头直接回答核心问题；教程交代完成后可验证的结果，不从百科式背景开始；
- 一次只引入当前理解所需的概念；
- 概念解释和教程围绕一条主路径展开，替代方案只在影响决策时说明；文章解读遵循来源实际的主线与分歧；
- 实践步骤给可见结果或明确的验证方式；
- 术语首次出现时给白话解释；
- 排错建议对应具体现象和原因；
- 示例可运行时实际验证，不能验证就诚实标注；
- 使用简洁自然的中文，中英文之间留空格，代码注释保持简短；
- 不使用空泛的“至关重要”“深入探讨”“精彩旅程”等 AI 套话；
- 用户需要行动建议时给具体下一步；文章解读可在作者的结论处结束，不强行附加练习或泛泛鼓励；
- 陪练模式的输出是问题而不是讲解，一次一问，不套用本页的教程章节结构和项目教程清单。

## 质量清单

### 概念解释

- [ ] 目标、读者基础和边界明确；
- [ ] 先说结论，再解释机制；
- [ ] 在需要时提供类比并标明失真边界；
- [ ] 例子中的事实、数字和数据有来源或明确是假设；
- [ ] 按回答尺度提供必要的误解、边界和练习，不给短问答硬加自测题。

### 文章解读

- [ ] 来源与成稿回答相同的核心问题，标题、开头和篇幅没有把支撑论点提升成主题；
- [ ] 读者能理解作者为什么得出结论，而不只是得到几条并列知识点；
- [ ] 关键场景、转折、反例、条件和观点归属保留，风险没有被加强成确定因果；
- [ ] 术语有白话解释，解释者补充与来源内容可区分，没有新增动机或情绪；
- [ ] 覆盖范围与来源定位清楚，没有为了套教学模板增加无用章节。

### 项目教程

- [ ] 主线项目足够小，能在合理时间完成；
- [ ] 版本、依赖、环境和假设已标注；
- [ ] 每一步都有动作、结果和验证；
- [ ] 最终项目有完整运行路径；
- [ ] 练习有明确目标和检查方式；
- [ ] 完成标准是可判定的能力描述，不是章节勾选；
- [ ] 每步的检查点要求读者先作答，最终测评覆盖全部子技能并有整合题；
- [ ] 未运行的命令和未验证的输出已标注。

### 陪练

- [ ] 只在用户明确要求被考核时启用，模糊请求先确认一次；
- [ ] 诊断在讲解之前完成，子技能数量在 4–10 之间；
- [ ] 每次只问一个问题并就停止，问题后没有夹带提示或答案；
- [ ] 级别有 2 次以上独立检验支撑，含糊回答没有被判为正确；
- [ ] 进度图与状态块只出现在会话里，没有写进教程或文件；
- [ ] 全部达标后做了混合测评，而不是在最后一个问题上直接收尾。
