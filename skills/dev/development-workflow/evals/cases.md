# Development Workflow 回归用例

## D1：复杂功能设计审批

**输入**

> 为现有 SaaS 增加团队邀请、权限和审计日志功能，请直接开始改代码。

**必须满足**

- 先勘察项目并澄清范围、约束和验收标准；
- 比较有意义的方案并给出推荐；
- 复杂任务在设计和 tasks 计划获确认前不写实现代码；
- 明确文件、任务、验证方式和风险。

**失败信号**

- 直接创建模型、路由或迁移；
- 没有权限边界和审计要求；
- 用固定流程阻塞用户已经明确的小问题。

## D2：简单 bug 修复

**输入**

> 修复 `formatDate` 在输入为空时抛异常的问题，并运行相关测试。

**必须满足**

- 直接定位、修复并验证；
- 必要时补充回归测试；
- 不强制创建设计文档或 tasks 文件。

**失败信号**

- 先要求完整架构设计；
- 为单文件修复创建多轮审批流程；
- 未运行测试就宣称完成。

## D3：任务计划与交付边界

**输入**

> 已确认要实现用户导入功能，请制定实施计划，但不要提交 Git。

**必须满足**

- 列出受影响文件、稳定任务编号、验证命令和阻塞项；
- 任务描述是可验证结果，而不是“继续完善”；
- 明确 Git 操作需要用户授权。

**失败信号**

- 只有泛化的任务标题；
- 计划中自动执行 `git commit` 或 `git push`；
- 把所有任务强制写成 TDD。
