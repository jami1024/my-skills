# Go 包边界与架构决策

在任务确实涉及模块划分、依赖方向或生命周期时读取。核心规则与验证清单见 [`../SKILL.md`](../SKILL.md)，本文只解释如何作工程选择，不规定统一目录或技术栈。

## 从变化和约束出发

先确定本次要改变的行为、调用入口、依赖与对外契约，再决定是否需要调整边界。已有项目优先保持命名、包位置和依赖方向。新项目从能清楚表达当前需求的最小结构开始。

| 当前情况 | 优先考虑 | 需要拆分的信号 |
| --- | --- | --- |
| 单一入口、少量行为 | 同一个 package，按职责分文件 | 一个职责难以单独理解或测试 |
| 多个业务能力独立变化 | 按能力组织包，如订单、库存 | 跨能力修改频繁，边界开始混杂 |
| 多种协议入口复用业务规则 | 将协议适配与用例分开 | 同一规则被 HTTP、RPC 或任务入口重复实现 |
| 需要持久化或外部服务 | 在实际调用处明确依赖与资源所有权 | 第三方类型散落到不需要它的业务代码 |
| 多个可执行程序 | 共享稳定职责，入口分别组装 | 启动配置或生命周期不同 |

这些情况可以组合，但不必每项都建一个包。没有数据库就不创建数据访问包，没有复杂业务规则就不增加纯转发的 service 层。

## 包的职责与可见性

- 一个包围绕一个可解释的职责，优先选择业务能力或稳定的技术边界，避免不断膨胀的 `common`、`base`、`utils`。
- `internal/` 用于限制导入范围；`cmd/` 适合多个可执行入口；可复用库也可以直接放模块根包，不强制建立 `pkg/`。
- 同一包可以放多个文件；拆文件不要求同时拆包。只有职责、变化频率或导入边界需要独立时才新增包。
- 目录名不构成架构保证。已有项目使用 `service`、`repository` 或按业务能力组织时，沿用其方式，不改名套模板。

## 协议、业务与外部依赖

先明确职责，再决定是否分别建包：

- **协议边界**处理输入、传输层校验、身份信息和响应；复用用例时，不把某个 HTTP 框架的请求对象传入业务逻辑。
- **业务用例**表达操作权限、业务不变量和依赖编排；共享规则有稳定归属，避免多个入口各自复制。
- **外部适配**负责数据库、RPC、消息与文件等具体交互；业务需要隔离的驱动错误在这里转换，其他错误保留诊断原因。
- **应用入口**创建配置、连接和服务，明确哪些资源要关闭、谁负责关闭。

简单功能可以在同一包中完成这些职责。增加适配层应当减少真实耦合，不能只转发调用或改一个方法名。

## 接口与依赖方向

接口由需要替换或隔离依赖的使用方定义，方法只覆盖实际调用。直接依赖一个具体类型足够清楚时，不必增加接口。

通过构造函数显式传递必要依赖；小型程序手工组装即可。项目已经使用注入工具时复用其配置，不因为参考资料中出现某个工具而迁移。

遇到循环依赖时，先判断职责是否放错位置、数据类型归属是否清楚、调用方向是否混杂。移动接口可以解决部分问题，但不能把所有类型搬进公共包来掩盖循环。

## 数据模型和错误契约

传输结构、领域对象和持久化记录只有在字段、校验或变化方向确实不同时才分别建模。需要隐藏密码、哈希或内部字段时，在序列化边界显式控制输出。

业务需要稳定判断“未找到”“冲突”等结果时，复用项目已有的 sentinel 或错误类型；数据访问代码将对应驱动错误转换为该契约。协议边界再决定状态码或 RPC 状态，不把协议状态写进通用领域错误。

现有公共接口已经暴露驱动类型时，先确认兼容性和调用方，逐步迁移；不能为清理分层擅自改变对外行为。

## 事务与副作用

- 用例确定哪些变更必须保持一致，项目已有的数据访问边界执行事务；已有事务回调或工作单元按原方式复用。
- 同一事务内的读写使用同一事务句柄与请求 context，避免混用普通连接。
- 不把数据库事务对象扩散到不需要数据库细节的调用方，也不为简单的原子写入引入通用事务框架。
- 外部请求、消息和数据库提交无法仅靠本地事务保证一致。先说明失败、重试与幂等语义，有实际一致性要求时再评估 outbox 等方案。

## 生命周期和可测试性

共享客户端、连接和服务器通常由应用入口创建；请求级依赖和取消信号由请求拥有。构造失败要清理已经创建的资源，关闭顺序与依赖关系一致。

接口、时钟或客户端替换只覆盖真实外部边界。测试优先断言行为和契约，不为便于 mock 给每个类型建接口，也不使用与生产数据库语义不一致的替身来证明事务或锁行为。

## 方案说明应回答什么

1. 本次涉及哪些行为和包，哪些对外契约需要保持？
2. 哪些边界已有，为什么需要新增或调整？
3. context、错误和资源所有权如何传递？
4. 用什么测试验证成功、失败、取消和兼容性？
5. 是否新增依赖、迁移或部署步骤，为什么现有方式不够？

如果现有结构已经满足需求，直接在原结构中完成修改。架构说明应与改动规模相称，不为小任务生成完整分层设计。
