# code-reading 回归用例

## C1：模块实现调研（正例）

**输入**

> 分析一下 etcd 的 MVCC 存储是怎么实现的

**必须满足**

- 先锁定目的：关心读写路径，还是整体存储架构（含糊时问一个聚焦问题）；
- 尝试把项目跑起来（或跑该模块的测试），并说明是否成功、用了什么构建/运行命令；
- 先给横向架构，再纵向追一条具体路径；
- 结论标注 `[verified]` / `[static]`，并给出比例；
- 产出结构化读码报告（架构图 + 核心数据结构 + 调用链 + 黑盒清单 + 设计点评），而不是只有聊天回答。

**失败信号**

- 只列文件树和包结构就下架构结论；
- 把静态推断写成确定事实，无 `[static]` 标注；
- 没有明确目的就开始通读整个仓库。

## C2：单个函数或概念（反例）

**输入**

> 解释一下这个 `processInputBuffer` 函数在做什么

**必须满足**

- 不走完整 9 phase 工作流，不产出读码报告；
- 直接解释函数职责、输入输出和关键分支，必要时读上下文；
- 可以提示用户：若要理解它在整条流程中的位置，可以走 `code-reading`。

**失败信号**

- 为一个函数启动环境编译、下断点、产出多章节报告；
- 强行生成 `code-reading-report.md`；
- 套用"先横向后纵向"等完整阶段。

## C3：环境不可运行（边界）

**输入**

> 分析这个嵌入式固件仓库的启动流程（仓库需要特定硬件，本地无法编译）

**必须满足**

- 明确声明项目未能运行、原因，以及已尝试的步骤；
- 回退到测试/临时日志/带标注的静态追读；
- 报告中 `[verified]` 极少或为零时显式说明，给出 `[static]` 比例；
- 不伪造运行结果、命令行输出或 `file:line` 引用。

**失败信号**

- 输出格式完整但未说明环境不可运行，让人误以为结论经运行验证；
- 声称"已运行/已验证"却没有可复现命令或调用栈；
- 编造不存在的文件、函数或行号。

## C4：bug / 性能调用链排查

**输入**

> 这个服务在并发请求下偶发超时，帮我沿着调用链定位可能的阻塞点

**必须满足**

- 以情景分析为主：构造触发输入、在入口/可疑点下断点或加日志、抓调用栈；
- 用核心数据结构（锁、队列、连接状态等）解释阻塞的成因；
- 区分"已观察到的路径"与"推测"（`[verified]` / `[static]`）；
- 至少给出一条设计层面的取舍点评（Phase 8）。

**失败信号**

- 只做静态代码扫描、不构造任何场景就给出根因；
- 把某个可疑函数直接断言为根因而无证据；
- 跳过 Phase 7，不看共享数据结构与生命周期。
