# Explain 回归用例

## E1：短概念解释

**输入**

> 用不懂后端的产品经理能听懂的话解释什么是幂等性，最好用支付场景举例。

**必须满足**

- 先给一句话结论，再用生活化例子解释；
- 明确幂等和“每次都成功”不同；
- 使用支付请求、请求 ID 或重复提交说明风险；
- 避免无关实现细节。

**失败信号**

- 只贴 HTTP 规范术语；
- 把幂等解释成缓存；
- 没有说明重复请求的结果。

## E2：项目驱动教程

**输入**

> 我会 TypeScript，想从零学会用 FastAPI 做一个带测试的待办 API。请给我分阶段教程。

**必须满足**

- 先说明目标、前置知识和最终产物；
- 按可运行的小步拆分，每步有命令、代码、预期结果和练习；
- 覆盖错误处理、测试和常见排错；
- 技术版本和依赖选择明确，不假设已经安装一切。

**失败信号**

- 只给概念目录，没有可运行步骤；
- 一次贴出无法验证的大型项目；
- 把不同版本 API 混在一起。

## E3：非适用请求

**输入**

> 请逐行审查这个仓库的认证实现，并直接修复漏洞。

**必须满足**

- 说明 explain 适合讲解，不替代代码审查和实现流程；
- 可以解释相关概念，但不假装已完成代码审查；
- 建议使用对应技术栈 skill 或 development-workflow。

**失败信号**

- 没有读取代码就判断存在漏洞；
- 输出教程代替风险定位和修复计划。

## E4：陪练模式

**输入**

> 我学过 Python 的列表和字典，也看过你之前给的教程。现在别讲，直接考我，一次一问。我说不会就换一个更窄的问题，不要直接给答案。

**必须满足**

- 不输出教程、章节或文件，先一次只问一个问题并停下来等回答；
- 诊断在讲解之前完成，用 3–5 个由易到难的问题定位起点；
- 按 0–5 级追踪 4–10 个子技能，级别变化或用户要看进度时渲染进度图；
- 答错先换更窄的问题暴露矛盾，连续 2–3 次失败才讲解，讲完换角度重测；
- 级别需要 2 次以上独立检验支撑，含糊回答没有被判为正确。

**失败信号**

- 一次抛出多个问题，或先讲解再提问；
- 直接给出答案，或凭一题答对声称“已经掌握 4 级”；
- 把进度图或状态块写进文件或教程正文；
- 输出长篇讲义代替提问循环。

## E5：学习请求但意图不明

**输入**

> 想深入学一下 React 的 hooks。

**必须满足**

- 按学习请求处理，并用一句短问题确认要材料还是进入陪练；
- 不直接开启几十题的诊断，也不立刻交付数十页教程。

**失败信号**

- 未经确认就开始提问考核或要求用户先答题；
- 忽略确认需求，直接生成完整教程并附上进度条。
