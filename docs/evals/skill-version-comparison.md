# 原版与优化版 skill 实际对照

## 结论

本轮支持“降低了本批任务的上下文用量”，不支持“所有任务效果无损”或“运行更快”。核心回答大体保留，参考拆分场景未发现漏读，但仍有事实和验证计划错误。优化版在两轮中各出现一次值得修复的问题：归档扩大原子性保证、计划要求已满足的行为先失败。

建议保留当前结构精简，不整体回滚；先补足证据边界和既有行为保护，再针对失败场景复测。以下是有限样本人工审阅，不是总体成功率或统计显著性结论。

## 设计与证据

- 原版：优化开始前的 Git HEAD `0b419d3328029ec14874b0bd5b94756f7408fef2`，通过 `git ls-tree` / `git show` 导出，仅做 Git 只读操作。
- 优化版：本轮评估开始时的工作区正文和参考资料，逐文件 SHA-256 保存在运行 manifest 中；评估期间未改 skill。
- 模型：`deepseek/deepseek-v4-flash-vision-exp`，thinking=`low`。
- 8 个用例 × 2 个版本 × 2 轮，共 **32 次正式模型运行**；每版 16 次。
- 两版使用相同提示词、只读工具和项目夹具；独立无会话进程，关闭上下文文件、其他 skills、扩展及 MCP，只注册并显式调用目标 skill。
- 两个进程并发运行；每轮交替提交版本顺序，未控制远端排队、缓存状态和服务负载，因此耗时只做描述。
- 日志核对：32 次均退出码 0，最后 assistant 消息均正常结束；实际 read 路径指向对应版本正文，没有发现跨版本读取正文或参考文件。
- 试运行因原版目录参数错误未完成对照，且并非有效原版快照，**不计入正式样本**。正式记录使用独立目录，未混入试运行。

原始证据位于仓库忽略的 `.tmp/skill-version-compare/`：

```text
manifest.json                 # 两版来源、文件哈希、完整输入和断言
results.json                  # 32 次运行的用量、耗时、读取路径
summary.json                  # 聚合指标
runs/round-{1,2}/{original,optimized}/
  <case>.jsonl                # 原始工具与模型事件
  <case>.answer.md            # 最终回答
  <case>.stderr
  <case>.result.json
tutorial-program-checks.json  # 教程完整程序的追加执行检查
```

执行脚本为 `.tmp/run-version-compare.py`，同样未提交。原始数据应在清理 `.tmp/` 前单独备份；本页保留判定和指标，不代表忽略目录中的证据已进入版本控制。

## 上下文、输出与耗时

下表按每个版本的 16 次正式运行汇总：

| 指标 | 原版 | 优化版 | 变化 |
| --- | ---: | ---: | ---: |
| 累计输入 token，含缓存读取/写入 | 182683 | 122794 | −32.8% |
| 模型事件报告的累计 totalTokens | 220948 | 167657 | −24.1% |
| 最终回答字符数 | 46634 | 48249 | +3.5% |
| 各次运行耗时之和（秒） | 206.6 | 230.2 | +11.4% |
| read 尝试次数 | 45 | 45 | 不变 |
| read 工具报错次数 | 9 | 6 | 减少 3 次 |

输入 token 来自原始 assistant `usage` 的 `input + cacheRead + cacheWrite` 累加，包含多轮工具调用中重复进入上下文的内容，不是单次 prompt 大小，也不是收费金额。totalTokens 使用供应商报告值，未把 reasoning 另行叠加。缓存和并发状态未锁定，不能将该比例外推到其他模型、长任务或实际费用。

工具报错主要为读取不存在的测试路径、AGENTS.md 或将目录作为文件读取，不是程序测试失败。两轮不足以证明工具错误率有稳定改善。

最明确的反例是教程：优化版两轮都更长，平均回答增加约 15.8%，耗时增加约 30%。skill 更短并不保证输出更短或更快。

## 逐场景人工审阅

不把“会话正常结束”当成内容全对。以下同时检查题目中的核心要求和额外事实错误，因此不提供掩盖差异的单一通过率。

### 1. explain：一句话解释

两版两轮都直接解释缓存，没有额外章节、练习、计划审批或写文件。没有观察到缩短后的关键能力丢失；原版本身也能遵守短答要求，因此没有足够证据称优化带来新的正确性收益。

### 2. explain：完整教程

两版两轮都围绕内存待办列表，包含函数、列表、字典、完整代码、两个练习与预期输出，均明确未执行，不停留在审批。

追加验证：从 4 份回答中分别提取最长的完整 Python 程序，人工/AST 检查不含导入、文件或外部执行操作后，在独立 `python -I` 子进程运行。**4 份程序退出码均为 0，标准输出均与各自教程给出的对应预期输出一致。**

本机实际解释器是 Python 3.14.3，不是输入要求的 Python 3.11；已用 `ast.parse(feature_version=(3, 11))` 检查所提取主程序语法，但这不等于 3.11 运行兼容性验证。没有逐步执行所有增量片段和练习，不能称完整教程已端到端验证。

未发现主程序退化，但优化版更啰嗦。精简的是 skill 读取，而非回答长度。

### 3. draft：演讲与文章

两版两轮都交付 Markdown，保留提供的作者/演讲者、标题及主要观点，缺失日期和 URL 不补造，未生成图片。

- 原版演讲第 1 轮增加“现场演讲”，输入未说明现场载体；两轮使用“观看/收听入口”字段，仍带节目模板痕迹。
- 优化版两轮明确“仅覆盖片段，未通读完整演讲”，使用素材对应的演讲/作者/来源字段，语境更贴合。
- 原版文章第 1 轮额外解释“不是播客或访谈、未提供节目和嘉宾”，虽未捏造，但属于无关模板噪音；优化版没有这一段。
- 配图提示词两版都有生成，用户只禁止实际生成图片，不能据此判为违规。优化版部分提示词同时要求画面出现文字标签又写“图中文字：无”，仍有内部一致性问题。

这两例主要体现模板适配改善，不构成长文写作质量或事实准确率的广泛结论。

### 4. development-workflow：已确定方案的任务计划

两版均列出行为、文件、大小写重复、正常路径及零写入验证，没有预写完整生产代码，也没有执行 Git 写操作。

夹具已经包含去重实现和根目录 `test_importer.py`，而提示提到 `tests/test_importer.py`；这用于观察是否先核实现状，但也使计划评估存在路径冲突因素。

- 原版第 1 轮发现已有实现与根目录测试；第 2 轮只根据请求路径不存在就提出新建 `tests/test_importer.py`，并给出未由 README 支持的 pytest 命令。
- 优化版两轮均发现根目录测试；第 1 轮建议按缺口决定是否修改，比固定实现计划更合适，但仍列了可选 pytest 命令。
- **优化版第 2 轮出现明确问题**：已读到去重存在，却要求 T2 的重复拦截用例在实现前“预期失败/缺失”，T3 后“由红转绿”。对于已满足行为，这个预期没有依据。不应为了测试优先而制造失败或重复实现。
- 原版第 1 轮交付计划后追问“需要我按此计划执行吗”；优化版未出现同一句，但用户本来只要求计划，不能把结尾问句直接当作阻塞执行的证据。

因此这里不能宣称稳定无损，应补充“已有行为可直接通过，按缺口修改”的规则与回归场景。

### 5. project-archive：局部功能归档

两版两轮都读取了提供的四个项目文件。原版功能模板在主文内，优化版两轮都实际读取 `templates/feature-context.md`，未出现模板拆出后漏读。

两版均解释了 strip/lower、批内查重、重复时提前抛错、内存 store 写入、diff 前后变化及测试未运行。

- 原版第 1 轮把 skill 的版本日期放入归档时间，并将未在 diff 出现的测试说成本次新增，证据不足。
- 优化版第 1 轮没有上述日期问题，但声称：**“对内置 list 而言，正常与异常路径均为整批生效或整批不生效”**。这把重复检测阶段的保证扩大到了写入阶段，结论错误。
- 优化版第 2 轮正确指出 `dict(row, ...)` 或 `extend` 中途失败可能保留部分写入；但把测试文件标为“修改/补充”，当前文件存在本身不足以证明历史变更。
- 原版第 2 轮也把测试标为修改，说明历史归属不实并非优化版独有。

追加最小复现：第一行使用正常 dict，第二行使用能读取 email、但 `keys()` 抛出 `ValueError` 的映射对象。规范化与查重均通过，`list.extend` 写入第一行后在复制第二行时出错，store 仍保留第一行。这实证否定了优化版第 1 轮的广义原子性陈述；不影响“重复检测阶段失败时不写入”的正确结论。

这里应保留精简后的按需模板，但加强“保证成立的条件”和“当前快照不能证明历史状态”的约束。

### 6. FastAPI：目录、事务与旧版本

两版两轮均保留按领域组织的目录及 Pydantic v1，明确 repository 不自行 commit、同一用例统一事务、任一写入失败整体回滚，并给出失败注入验证点。

优化版两轮实际读取了拆分后的 `project-structure.md` 及职责参考；第 2 轮还读取索引，没有发现详细参考漏读。原版读取了旧版完整架构文件及较长的开发流程参考，累计输入明显更高。

仍存在额外示例风险：优化版第 2 轮的 `async with db.begin()` 旁写“若 session 已 autobegin，则复用现有事务”。单独这段代码不会自动复用活动事务，缺少实际分支处理；原版相应回答则提醒重复 begin 会报错。该处是建议代码中的技术瑕疵，未运行真实 SQLAlchemy 集成，不能称生成代码验证通过。原版也有“第三个及以上领域才评估分层”之类缺乏依据的阈值。

核心判断未见退化，完整代码正确性仍不能保证。

### 7. golang-how-to：只配置路由

两版两轮均读取对应版本的 Configure 参考，只输出 AGENTS.md 路由规则，没有强制 11 个主题，也没有要求修改其他客户端或重复审批。

原版仍引用“约 100 tokens/描述、11 个约 1100”的文档估算，且容易把新增配置规则与注册 description 的开销混为一谈；优化版不再给固定数值，主要区分正文读取与注册开销。

该场景明确要求 routing-only，未评估自然请求的路由准确率，也没有评估“新建服务却不应改配置”的实际写入行为。

## 未覆盖与解释限制

1. 仅一个模型、thinking 档位和每例两轮，样本不足以判断稳定性。
2. 正文强制调用用于比较版本，不是自动触发测试。详细参考读取也由输入明确要求，因此只能证明按要求可找到，不证明模型会自行按需选择。
3. 既有五个自有 JSON 用例参与了本轮优化设计，不是独立留出集，可能高估效果。
4. 修改不仅减少字符，还改变审批、素材分支和事务示例；无法把结果差异单独归因于“变短”。
5. 仅只读建议与文本输出；未执行真实服务实现、数据库集成、知识库入库或失败恢复。
6. 未覆盖 React、library、handoff-summary、code-reading 的完整行为对照。
7. 运行器 `valid` 只表示调用条件有效，不代表内容正确；事实和技术问题由人工审阅保留，没有用模型自评分代替判定。

## 建议的下一步

优先补 3 条小约束及配套反例，再用新样本复测：

- 已有行为和测试可直接通过，不要求人为先红后绿；仅实现真实缺口。
- 区分校验前不写入、写入中途部分失败及完整事务，不将局部保证扩大为普遍保证；不能从快照推断测试新增/修改历史。
- 示例涉及 SQLAlchemy 活动事务时必须明确事务所有者，不用注释代替 `begin()` 前置条件处理。
