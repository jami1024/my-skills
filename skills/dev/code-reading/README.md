# 读码工作流 Skill

**版本**: v1.0.0
**语言无关**: ✅
**来源**: 收录并本地化自 [lichuang/how-to-read-code](https://github.com/lichuang/how-to-read-code)（Apache-2.0）；方法论出自 codedump《如何阅读一份源代码？》（2020 中文原版 / 2021 英文版）

系统化阅读陌生代码库，并产出一份结构化读码报告。

## 概述

大多数 agent 面对"这个项目是怎么实现的？"只会静态列文件、凭猜发作答。本 Skill 强制一套经过验证的读码方法论：

- **先跑起来** —— 深入阅读前先让项目编译并运行；把调试干扰降到最低（单进程、`-O0 -g`）。
- **明确目的** —— 读之前先有一个聚焦问题，之后一切以它为准绳。
- **区分主线与支线** —— 主线纵向精读；支线当黑盒，只记录对外接口。
- **先横向后纵向** —— 先整体架构，再追具体执行路径。
- **情景分析** —— 构造真实输入、在入口下断点、抓调用栈：跑出来的路径是事实，不是猜测。
- **测试用例即场景文档** —— 把项目自带测试当作现成的阅读入口。
- **数据结构优先** —— 先梳理核心数据结构及其关系，它们定义了架构。
- **没有产出等于没读** —— 每次都以书面报告收尾（图 > 文 > 代码）。

最终交付物是一份**读码报告**：范围与目的、架构图、核心数据结构关系、目标流程的纵向分析、有意未展开的黑盒清单、设计点评与开放问题。每条结论都标注 `[verified]`（经运行/调试/测试验证）或 `[static]`（仅静态推断），并在开头给出二者的比例——哪些是实锤、哪些是猜测，一目了然。

## 适用场景

### 使用本 Skill

- "帮我读一下这个项目"、"调研一下这个仓库"
- "分析某模块 / 某流程的内部实现"
- "X 是怎么工作的"（需要真正追到代码路径，而不是给个概念）
- "为什么会出 bug / 变慢"——需要沿调用链定位

### 不使用

- 解释单个函数、单个概念或技术原理 → 用 `explain`
- 代码审查、需求设计、任务拆解 → 用 `development-workflow`
- 只想要一份文件清单、符号索引或逐行讲解
- 需要修改代码或提交 Git（本 Skill 只读；Git 写操作需用户授权）

## 与其他 Skill 协同

```
code-reading（本 Skill）      →  读懂现状，产出读码报告
        +
development-workflow          →  基于读懂的结果做设计、拆任务、审查
        +
fastapi / golang / react      →  具体技术栈的实现约定
```

## 核心内容

### 9 个 phase

| Phase | 名称 | 要点 |
|---------|------|------|
| 1 | 先跑起来 | 最小可调试环境；设预算上限，跑不起来就记录原因并回退 |
| 2 | 明确目的 | 含糊时先问一个聚焦问题；把目的写进报告 Scope |
| 3 | 主线 vs 支线 | 主线纵向精读，支线只留接口记录 |
| 4 | 先横向后纵向 | 先架构后路径；新细节改变架构图时先更新图 |
| 5 | 情景分析 | 构造真实输入 + 断点 + 调用栈；观察到的路径是 ground truth |
| 6 | 测试用例即场景 | 跑一个测试胜过读十个文件 |
| 7 | 数据结构优先 | 画清归属/生命周期关系；与 Phase 5 交替 |
| 8 | 主动提问 | 为什么这样设计？换我会怎么做？有无可疑代码？ |
| 9 | 写报告 | 图 > 文 > 代码；不粘贴大段代码 |

### 深度裁剪

不是每个任务都要跑满 9 个 phase。`SKILL.md` 里有一张"目的 → 该跑哪些 phase"的对照表，覆盖"单个机制/整体项目/bug 排查/是否采用"四类目的，以及需要拒绝的反模式。

## 样例可信度

`examples/` 下的 Redis 报告是真实产出：`make noopt` 真编译、redis-cli 实测驱动、lldb 抓取调用栈（4.1 节就是实际抓到的栈），全部 `file:line` 引用经人工比对锁定 commit（`1f245638`）核验。

## 本地化改动

相对上游 `lichuang/how-to-read-code` 的差异，便于日后同步：

1. 目录名与 `name` 改为 `code-reading`，落位 `skills/dev/`；正文与模板译为中文。
2. `description` 改为单行、触发语前置（上游用 YAML 折叠标量 `>-`，本仓库校验脚本无法解析；且上游描述前半段是方法论清单，不利于路由）。
3. Phase 1 增加**预算上限**：最多约 3 轮构建尝试或不超过总投入的约 1/5，超限即回退并写明原因（上游只说"跑不起来就声明"，容易吞掉整个任务预算）。
4. 报告要求增加 `[verified]` / `[static]` **比例统计**，防止在不可运行的环境里输出一份格式完整、实则全为静态推断的报告；并明确报告落盘路径与写盘受限时的回退。
5. 新增 `evals/cases.md` 与 `README.md`；`examples/` 保留但明确不默认加载。
