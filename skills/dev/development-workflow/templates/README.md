# 开发文档模板

这些模板对应不同生命周期产物，**不建议合并成一个大模板**。合并会让简单任务也携带需求、设计、ADR、评审和执行字段，增加填写成本并降低追踪清晰度。

## 哪个是主模板

没有唯一的“总模板”，但可以这样理解：

- **需求主线**：`requirement-template.md`，负责定义为什么做、做什么和验收标准；
- **技术主线**：`design-template.md`，负责说明怎么实现，是大多数工程任务的核心技术文档；
- **执行主线**：`tasks-template.md`，负责追踪实际实施和验证，不替代需求或设计。

如果只能选一个：面向业务对齐选 `requirement-template.md`；已经明确需求、准备开始技术实现时选 `design-template.md`。

## 需求文档和设计文档的区别

| 对比 | 需求文档 | 设计文档 |
|---|---|---|
| 核心问题 | 为什么做、做什么、做到什么算成功？ | 准备用什么方案实现、为什么这样实现？ |
| 主要读者 | 用户、产品、业务和项目负责人 | 开发、测试、运维和评审者 |
| 关注内容 | 目标、范围、场景、验收标准、边界 | 架构、模块、接口、数据流、技术取舍、验证方案 |
| 是否依赖技术栈 | 尽量不依赖具体实现 | 可以明确技术和实现约束 |
| 变化原因 | 业务目标或范围变化 | 方案、约束或技术实现变化 |

一个简单判断：**如果换掉实现方式，文档仍然成立，通常属于需求；如果换实现方式就必须重写，通常属于设计。**

例如“用户可以导入 CSV，重复用户不能被创建”是需求；“使用流式解析、临时表和唯一约束保证导入幂等”是设计。

## 选择哪个模板

| 需要回答的问题 | 模板 | 适用时机 |
|---|---|---|
| 为什么做、范围是什么、怎么验收？ | `requirement-template.md` | 需求尚未稳定，或需要和业务方对齐 |
| 准备怎么做、有哪些取舍、如何验证？ | `design-template.md` | 涉及多模块、接口、数据或技术选型 |
| 为什么选这个长期方案？ | `adr-template.md` | 需要记录可追溯的架构决策 |
| 当前方案能否交付、风险在哪里？ | `architecture-review-checklist.md` | 设计评审或上线前评审 |
| 谁做什么、做到哪一步、如何证明完成？ | `tasks-template.md` | 中等/复杂任务的实施追踪 |

## 推荐链路

```text
requirement → design → ADR（如需要）→ tasks → architecture review（如需要）
```

不是每个任务都要创建全部文档：

- 简单修复：回复 checklist 或短计划即可；
- 中等任务：通常使用 requirement/design/tasks 中的一个或多个；
- 复杂任务：先完成需求与设计，再创建 tasks；重要架构变更补 ADR 和评审清单。

## 实际使用顺序

| 情况 | 推荐顺序 | 说明 |
|---|---|---|
| 简单 bug、文案或配置修改 | checklist → 实现 → 验证 | 不必为了形式创建正式需求文档 |
| 需求已经明确、技术方案简单 | 简短需求确认 → design → tasks | 可以把需求确认写在 design 开头，不必重复生成完整需求文档 |
| 需求本身还不清楚 | requirement → design → tasks | 先解决目标、范围和验收，再讨论实现 |
| 多模块功能或架构变更 | requirement → design → ADR（如需要）→ tasks → review | 设计和关键决策确认后再拆实施任务 |

**不要直接从模糊需求生成 tasks。** Tasks 需要明确的方案、受影响文件和验证方式；如果这些还不清楚，应先补需求或设计。反过来，如果用户已经给出了完整需求，也不必机械重写一份需求文档，可以直接提炼验收标准并进入 design。

## 共用规则

- 只保留对当前任务有帮助的章节，按需删除标记为“可选/按需”的部分；
- 任何待确认事项都要写明状态、负责人或下一步，不要把假设伪装成决定；
- 每个验收标准、决策或任务都应有可执行的验证方式；
- 文档之间通过主题名、编号或相对链接互相引用；
- 模板中的示例编号、日期、路径和负责人必须替换，不能原样交付。
