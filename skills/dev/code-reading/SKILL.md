# 读码工作流

像资深工程师一样阅读陌生代码库，而不是像游客一样走马观花。本流程把 codedump 的读码方法论（[如何阅读一份源代码？](https://www.codedump.info/zh/post/20200605-how-to-read-code/)）转化为 agent 可执行的步骤。

## 核心原则：读码必须留下产出

被动地"看一眼代码"只能得到肤浅的理解。本流程的每个 phase 都必须以**可留存的东西**收尾：一条笔记、一张图、一个可复现的用例、一份书面报告。某个 phase 没有产出，就等于没有发生。

**最终交付物是一份结构化的读码报告**（模板见 `templates/report-template.md`），不是一段聊天式的回答。

## 工作流程

按顺序执行下面的 phase。实践中 Phase 2–4 会来回交替，下面的顺序只是默认入口顺序。这些 phase 是**前置条件，不是官僚流程**——跳过它们，分析就会退化成浅层猜测。

### Phase 1 — 先跑起来

在深入读代码**之前**，先搭出一个最小可运行、可调试的环境。

- 找到构建说明（README、Makefile、CMakeLists、package.json、Dockerfile），让项目能编译并跑起来。
- **把干扰降到最低**：优先单进程、不开优化、debug 构建。
  - C/C++：`-O0 -g`，关掉 LTO。多进程服务（如 Nginx 风格）：worker 数设为 1，保证只有一个进程可 attach。
  - 优先使用 debug 入口（例如只跑一个测试二进制，而不是整个系统）。
- **预算上限（重要）**：环境搭建是有成本的，必须设上限——例如最多 3 轮构建尝试，或不超过本次任务总投入的约五分之一。超限就停下，在报告中写明"未能运行 + 原因 + 已尝试的步骤"，转入 Phase 5 的替代手段（测试 / 临时日志 / 带标注的静态追读），并相应下调结论的把握程度。
- 如果项目本地确实跑不起来（外部依赖、专用硬件、授权限制），必须明确说明，回退到测试用例 + 静态阅读。**不要隐瞒这个限制。**

退出条件：目标模块的代码路径能被一次真实执行触达，或者有一份写清楚"为什么不能"的记录。

### Phase 2 — 明确目的

绝不在没有目的的情况下开始读码。按下面的顺序确定目的：

1. 用户到底想知道什么？如果含糊，读之前先问**一个**聚焦的问题。例如："理解某个模块的实现" vs "理解整体框架架构" vs "理解某个算法"。
2. 把目的写下来，作为报告的 Scope 一节。之后每个 phase 都以这个目的为判断标准。

没有目的地通读全部代码，既浪费时间也消耗热情。这个 phase 可能把范围缩小十倍——务必用它。

### Phase 3 — 区分主线与支线

目的确定后，把遇到的每一段代码归类：

- **主线**：直接服务用户所述目的。纵向精读，逐行看。
- **支线**：其余一切。**当作黑盒**——只记录对外接口（名称、输入、输出、副作用），然后继续走。不要深入它的实现。

一个典型例子："这个 dict 是怎么实现的"在你只关心某个业务流程时就是支线——流程只是**用到**了它。

深入任何文件之前先自问："这是主线还是支线？"是支线 → 只留接口记录。

### Phase 4 — 先横向，后纵向

两个阅读方向，刻意交替：

- **横向**：跨模块，理解整体架构。面对陌生项目时**先**做这件事。
- **纵向**：沿一条执行路径顺序追下去，针对某个流程或算法。只有在有了横向上下文之后才做。

交替的规则：

1. **先整体后局部。** 全局图景不清楚之前，不要钻任何细节。
2. 遇到暂时不影响全局的函数/数据结构，把它当黑盒（输入/输出），记入报告的"黑盒"清单，继续走。
3. 一次纵向走完，回到横向检查：新细节是否改变了架构图？如果变了，先更新图再继续。

### Phase 5 — 情景分析

这是整套方法的核心技术。**构造具体场景并调试它**，而不是静态读代码、指望猜出流程。

- 挑一个与目的相关的入口函数，下断点（或加打印/埋点日志），然后跑一个能触发该路径的真实输入。
- 命中时抓取：调用栈回溯、关键变量值、各分支的走向。**一条调用栈就足以勾勒出整条流水线。**
- 覆盖主要场景重复几次（可行时再补一个边界/错误场景）。
- 无法使用调试器时，退而求其次：单元测试、小型复现程序、临时日志，或带明确"未验证"标注的代码追读。

理由：这能把"大海捞针"变成一个边界清晰的场景，而**观察到的路径是事实，不是推测**。

### Phase 6 — 测试用例即场景文档

好项目（如 etcd、Google 系开源项目）自带丰富测试。测试就是**现成的场景**：单场景、自包含的输入，各走一条路径。

- 把目标模块的测试当作 Phase 5 的入口来读，而不是事后补课。
- 跑一个测试并单步跟进，胜过读十个源文件。

### Phase 7 — 先理清核心数据结构

"程序 = 算法 + 数据结构"——实践中，**数据结构定义了架构**。"糟糕的程序员担心代码，优秀的程序员担心数据结构和它们之间的关系。"（Linus Torvalds）

- 找出少数几个核心数据结构（在大多数模块边界上反复出现的类型）。
- 用一张图画出它们的归属与关系（谁创建、谁持有、谁修改；指针还是拷贝；生命周期）。
- 房子的比喻：数据结构是建筑的框架，算法是房间。不知道框架，房间看得再仔细也会迷路。
- 这个 phase 与 Phase 5 交替进行，而不是排在它之后：读结构 → 跑场景 → 修正结构图 → 重复，直到用户的问题被回答。

### Phase 8 — 多问自己问题

不要只提取事实，要审问代码：

- 这个数据结构为什么适合这个问题？同类项目在相同场景用什么？
- 如果由我来设计，我会这么做吗？取舍是什么？
- 有没有可疑之处——死代码、重复逻辑、缺失的错误处理？

把答案（或开放问题）记进报告。输出质量与学习质量成正比；没问出口的问题就是丢失的洞察。

### Phase 9 — 写读码报告

像"给一个不熟悉这个项目的人"（或六个月后的自己）解释那样写最终产物。

规则（来自原方法论）：

- **图 > 文 > 代码。** 架构与数据结构关系用图（支持 mermaid 就用 mermaid）。
- **不要粘贴大段代码。** 大段粘贴是用假象代替理解；改用伪代码或精简片段。若确实需要逐行标注，建议 fork 一份带注释的版本（作者本人的做法：`etcd-3.1.10-codedump`）。
- 想象读者是几个月后的自己，为将来的重读做优化。
- 报告语言跟随用户使用的语言。

## 报告要求

最终交付物是一份报告（模板见 `templates/report-template.md`），至少包含：

1. 范围与目的（Phase 2），以及项目是否在本地跑起来（Phase 1）。
2. 架构总览（横向）——配一张图。
3. 核心数据结构及其关系——配一张图。
4. 目标流程的纵向分析——配调用路径 / 时序图。
5. 有意未展开的黑盒及其接口。
6. 主动提问与设计权衡点评（Phase 8），其中至少一条"如果换我会怎么做"。
7. 开放问题 / 建议的后续动作。

**置信度要求**：报告必须对每条结论标注 `[verified]`（经运行/调试/测试验证）或 `[static]`（仅静态推断），并在第 1 节给出 `[verified]` / `[static]` 的比例统计。若全部或绝大多数为 `[static]`（例如环境不可运行），必须写明原因——不得用格式完整的报告掩盖未经运行验证的事实。

**落盘要求**：报告写入项目根目录的 `code-reading-report.md`（或用户指定路径）。若环境权限不允许写文件，就把报告完整输出在回答里，并明确说明"未能落盘 + 原因"——不允许无声降级成一段口语化总结。

## 深度裁剪

不是每个任务都要跑满所有 phase。按用户目的裁剪：

| 目的 | 需要完整执行的 phase | 说明 |
|---|---|---|
| "X 是怎么工作的？"（单个机制） | 1, 2, 3, 4（轻）, 5, 7（仅 X）, 9 | 保持范围窄 |
| "整体理解这个项目" | 1, 2, 3, 4, 6, 7, 9 | 除非用户要求，不做深度纵向追读 |
| "为什么会出 bug / 变慢？"（排查） | 1, 5（重点）, 7, 8, 9 | 情景分析是主角 |
| "该不该采用 / fork / 借鉴它？" | 1, 2, 3, 6, 7, 8, 9 | 重点放在 6 和 8 |

需要拒绝的反模式：

- "把整个代码库通读一遍"却没有目的 → 先顶回去，拿到目的（Phase 2）。
- 只凭静态列文件就回答架构问题，没有场景验证（Phase 5）→ 把结论标为"仅静态分析"。
- 环境完全不可运行，却输出一份看起来完整、实则全是 `[static]` 的报告而不加说明。
