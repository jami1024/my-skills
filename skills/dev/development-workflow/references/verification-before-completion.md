# 完成前验证

本参考在准备说“已完成”“已修复”或“可以交付”之前读取。目标是用实际证据替代推测，不要求所有任务都运行同一套命令。

## 验证步骤

1. **回看验收标准**：列出本次变更必须满足的行为、文件或文档要求。
2. **选择最小充分检查**：根据改动类型选择测试、lint、类型检查、构建、链接检查、截图或人工走查。
3. **实际执行**：在当前工作区运行命令，不用旧日志、代码阅读或“应该没问题”替代执行。
4. **检查结果**：确认退出码、失败测试、警告和生成物；必要时检查关键输出，而不是只看最后一行。
5. **报告证据**：对每个关键验收项写明命令/检查、结果和未覆盖风险。

## 按改动类型选择验证

| 改动 | 至少检查 |
|---|---|
| 业务逻辑或 bug 修复 | 针对性测试 + 受影响回归测试 |
| API、schema 或数据库 | 类型/lint + 接口测试 + 迁移或构建检查 |
| 配置、脚本或依赖 | 语法检查 + 代表性命令或启动检查 |
| 文档、模板或 skill | 链接/结构检查 + 代表性示例或反例 |
| UI 或交互 | 构建检查 + 关键视口和核心流程走查 |

## 结果分类

- **通过**：关键验收项都有实际证据，没有已知阻塞。
- **部分通过**：核心路径通过，但存在明确未覆盖项；必须列出风险。
- **阻塞**：验证失败、环境缺失或无法复现；不要宣称完成。
- **未运行**：没有执行检查，只能报告未验证，不能写成通过。

## 交付格式

```text
验证：<命令或检查>
结果：PASS / FAIL / BLOCKED / NOT RUN
证据：<关键输出或观察>
风险：<未覆盖项；没有则写“无”>
```
