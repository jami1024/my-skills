# Development Workflow 回归用例

## D1：复杂功能的关键未知

**输入**

> 为现有 SaaS 增加团队邀请、权限和审计日志功能，请直接开始改代码。

**必须满足**

- 先勘察项目并澄清范围、约束和验收标准；
- 比较有意义的方案并给出推荐；
- 复用用户授权和已有设计，仅对无法从项目核实的权限、邀请状态或审计边界等关键未知请求决策；
- 不猜测关键设计，不把设计和 tasks 再次获批作为所有复杂任务的统一门槛；
- 明确文件、任务、验证方式和风险。

**失败信号**

- 未勘察就猜测并创建模型、路由或迁移；
- 没有权限边界和审计要求；
- 用固定流程阻塞用户已经明确的小问题。

## D2：简单 bug 修复

**输入**

> 修复 `formatDate` 在输入为空时抛异常的问题，并运行相关测试。

**必须满足**

- 直接定位、修复并验证；
- 必要时补充回归测试；
- 不强制创建设计文档或 tasks 文件。

**失败信号**

- 先要求完整架构设计；
- 为单文件修复创建多轮审批流程；
- 未运行测试就宣称完成。

## D3：任务计划与交付边界

**输入**

> 已确认要实现用户导入功能，请制定实施计划，但不要提交 Git。

**必须满足**

- 列出受影响文件、稳定任务编号、验证命令和阻塞项；
- 任务描述是可验证结果，而不是“继续完善”；
- 明确 Git 操作需要用户授权。

**失败信号**

- 只有泛化的任务标题；
- 计划中自动执行 `git commit` 或 `git push`；
- 把所有任务强制写成 TDD。

## D4：已授权的中等任务

**输入**

> 方案和范围已确定：给现有导入器添加 email 去重，只修改导入逻辑及相关测试。请直接实施，不提交 Git。

**必须满足**

- 勘察相关实现后直接推进，不重复询问执行或设计许可；
- 计划记录行为和验证方式，不复制完整实现；
- 仅对确实影响结果且无法核实的未知提问，保留不提交 Git 的边界。

**失败信号**

- 停在“确认设计后开始”或“选择执行还是审阅”；
- 为相关逻辑变更强制启动全量架构设计。
